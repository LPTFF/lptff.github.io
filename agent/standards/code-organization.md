# 高效代码组织标准

## 目标

让产品功能产物、Agent 资产和生成证据边界明确，使修改易定位、易验证、易回滚。

## 目录边界

- 产品源码放在 `src/`，页面放在 `src/views/`，可复用业务工具放在 `src/utils/`。
- 浏览器直接访问的静态资源放在 `public/`；大型采集快照放在 `src/public/data/`。
- 面向用户且被运行时直接导入的 Markdown 可留在产品目录，例如 `docs/investment-assistant.md`。
- Agent 规范、业务规划、产品设计、项目上下文、迭代记录、研究和自测证据统一放在 `agent/`。
- 构建脚本留在 `scripts/`；仅服务 Agent 生命周期的工具放在 `agent/tools/`。
- 自动生成声明、构建目录和本地验证报告不作为手写源文件修改。

## 组织原则

1. **按消费者归属**：运行时消费者需要的内容属于产品；只供 Agent 或维护者决策的内容属于 `agent/`。
2. **单一事实来源**：规则和事实只维护一份，入口文件只链接 canonical 文档。
3. **从业务到复用**：先在业务边界内实现；出现稳定复用需求后再抽取共享工具，避免提前建立通用框架。
4. **最小依赖面**：页面复用 Element Plus 和已有工具，不重复创建基础组件、格式化器或平行数据链。
5. **源文件优先**：优先编辑 `src/`、配置和脚本源文件，不直接编辑 `dist/`、自动声明或派生产物。
6. **批量但可归因**：同构搜索、编辑和验证应批量执行；结果必须能映射回具体文件、页面、来源或用例。
7. **行为变更可回滚**：架构或兼容性变化拆成逻辑提交；产品功能与 Agent 治理迁移不混入同一提交。

## 新功能落点

- 路由入口：`src/router/`。
- 页面与局部组件：`src/views/<domain>/`。
- 跨页面业务模型和纯函数：`src/utils/<domain>/`。
- 用户内容：`src/content/` 或运行时明确导入的产品文档。
- 示例静态数据：`public/<domain>/`，并明确其是否参与生产功能。
- 业务能力和设计决策：`agent/product/`。
- 执行与验收证据：`agent/context/`、`agent/verification/reports/`。

## 修改检查

每次变更确认：

- 是否把 Agent 过程产物误放进产品目录；
- 是否产生重复实现或第二份事实来源；
- 是否直接改了生成文件；
- 是否检查直接消费者、兼容路径和移动端行为；
- 是否能用最相关的测试、构建和真实页面流程证明结果；
- 是否能通过一个逻辑提交安全回滚。
