# 软件可信验证原则

这份文件是 [理论收藏卡片](../theories/software-trusted-verification.md) 经过项目判断后形成的最小执行规范，不是理论原文的替代品。理论卡片记录来源、适用边界、未知和复评条件；本文件只规定当前项目已经采纳、会影响 Agent 判断的部分。理论卡片或项目证据发生变化时，应重新判断是否更新本规范，不得静默扩展 Agent 的强制流程。

这套原则用于降低软件需求、实现、开发者理解与真实运行行为之间的偏差。它借鉴 Verification & Validation、Independent V&V、软件测试理论、统计可靠性分析和形式化验证方法，但不声称构成新的统一理论。

## 1. 先判断要求，再选择验证方法

每项重要要求开始前，先明确：

- 这是 Verification（是否按规格正确实现），还是 Validation（在预期环境中是否满足用途）。
- 需要什么可信的 Test Oracle：正式规格、业务规则、数据约束、协议、领域不变量、可信参考实现或真实消费者的可观察结果。
- 要观察的行为发生在哪个环境：源码、构建链、运行时、浏览器、接口、数据库、操作系统、部署环境或真实用户流程。
- 需要哪些反例、输入类别、状态转换和恢复路径。

不要因为某个测试工具已经存在，就让工具决定验证范围。

## 2. 结论必须受客观证据约束

编译、构建、类型检查和单元测试只能证明它们直接覆盖的性质。重要结论应由可复查的客观证据支持，例如静态分析、测试结果、真实执行、浏览器观测、接口响应、数据库状态、构建产物、运行日志或协议验证结果。

报告必须区分：

- **已验证**：证据直接覆盖的要求。
- **未验证**：已知没有执行或没有覆盖的范围。
- **失败**：观察到与 Oracle 或要求不符的结果。
- **无法验证**：受授权、环境或外部条件限制而无法取得证据。
- **未知**：当前证据不足以作出判断。

不得把“未观察”“未执行”或“无法访问”解释为默认正确，也不得把有限测试解释为百分之百可靠。

## 3. Verification 与 Validation 不得混淆

“构建成功”支持当前源码通过当前构建链；它不自动支持页面可用、接口兼容、数据正确、用户流程成功或部署环境正确。

当要求涉及真实运行环境时，验证环境必须匹配要求。例如：

- UI 要求：在真实浏览器中观察页面加载、DOM、点击、路由、网络、存储、刷新、错误状态和控制台。
- 接口要求：执行真实请求或目标兼容实现，检查方法、参数、认证、响应结构、错误和重试行为。
- 数据要求：检查真实来源、时间、结构、重复项、不变量和实际消费者。
- 部署要求：在目标或等价运行环境中观察构建产物和启动行为。

## 4. Oracle 优先独立于实现

测试不能只根据当前实现推导 expected result，否则测试和实现可能共享同一错误假设。优先从原始需求、正式协议、外部标准、业务不变量、可信参考实现或真实消费者建立 Oracle。

对于高风险行为，应引入独立验证思想：独立设计测试、重新解释需求、使用不同验证方法、独立 Agent 或独立参考实现。独立性用于减少共同错误假设，不是为了增加形式上的流程。

## 5. 优先验证 Property、Invariant 和状态转换

存在普遍规律时，优先表达为 Property 或 Invariant，而不只是积累有限样例。重点关注：

- 重复操作的幂等性和去重性。
- 失败、重试和恢复不会破坏已有有效状态。
- 集合型计算不受无关顺序变化影响。
- 没有新证据时，`partial` 不会升级为 `complete`。
- 权限、事务、同步和状态转换遵守业务不变量。

使用 Property-Based Testing 生成多类输入寻找反例。测试数量本身不等于输入空间覆盖率；至少考虑正常、空、边界、异常、部分、重复、权限不足、认证失效、网络失败、外部服务异常和不同运行环境。

## 6. 无法取得绝对输出时使用 Metamorphic Testing

当没有唯一可信的绝对输出时，验证输入变化与输出变化之间必须成立的关系，例如：

- 输入顺序改变，顺序无关的统计结果保持不变。
- 重复执行幂等操作，最终状态保持不变。
- 所有金额按相同比例缩放，纯比例指标保持不变。

Metamorphic Relation 不能替代业务 Oracle，但能在 Oracle 不完整时发现实现违反必要关系的错误。

## 7. Mock 只验证假设中的内部逻辑

Mock 证明的是“在外部行为符合假设时，内部逻辑如何运行”，不能证明真实 API、浏览器、数据库、认证系统、文件系统、网络、CLI 或协议实现符合该假设。

存在外部依赖时，按风险补充真实集成、契约测试或目标环境验证。Mock 成功不能替代真实兼容性证据。

## 8. 复杂状态系统补充形式化验证

对于并发、分布式协议、同步、重试、事务、去重、一致性、恢复和权限状态转换，有限样例可能遗漏关键状态组合。必要时建立 `State / Action / Transition / Invariant` 模型，用 model checking 或其他形式化方法搜索反例。

形式化 Verification 只证明模型满足性质；真实运行 Validation 还要证明模型、实现和外部世界相符。两者不能互相替代。

## 9. 真实缺陷必须沉淀为回归证据

真实运行发现并能稳定复现的缺陷，应转化为回归测试、Property、Invariant、Contract Test 或其他自动验证条件。目的不是增加测试数量，而是防止已知错误重新出现，并保留它的可信 Oracle 和复现条件。

## 10. 可靠性结论需要统计前提

“全部测试通过”只能描述观察到的样本和覆盖范围，不能直接推出故障概率为零或可靠性为百分之百。若需要统计结论，必须明确目标总体、样本生成方式、运行分布、独立性假设、成功/失败定义、统计模型、置信水平和区间计算方法。否则只报告执行事实、已覆盖场景、未覆盖场景和剩余未知。

## Agent 的最小判断循环

面对一个改动或完成声明，Agent 应按以下顺序判断，不需要机械生成固定模板：

1. 把需求拆成可观察的行为和不变量。
2. 标记每项行为属于 Verification、Validation，或两者都需要。
3. 为每项行为指定可信 Oracle，并检查 Oracle 是否独立于实现。
4. 选择匹配运行环境的证据：静态、构建、单元、集成、浏览器、接口、数据、部署或形式化验证。
5. 覆盖会显著改变行为的输入、外部依赖、失败路径和状态转换。
6. 对没有绝对 Oracle 的部分定义 Metamorphic Relation；对普遍规则定义 Property/Invariant。
7. 将真实失败转为回归证据。
8. 只根据已经取得的证据报告已验证、未验证、失败、无法验证和未知。

核心判断是：**证据是否直接支持这条具体主张，而不是代码是否看起来合理。**
