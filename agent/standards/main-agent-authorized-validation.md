# 主力 Agent—授权验证 Agent—人类裁决者协作标准

## 目的

本标准用于在有限 Agent 资源下完成涉及私人数据和真实用户环境的复杂产品任务，同时保持最小权限和人的可审查性。

默认结构是非对称的：

- **Agent A 是主力交付 Agent**，从理解需求到实现、静态排错和修复，常态承担 80% 以上工作；
- **Agent B 是授权真实环境验证 Agent**，只处理 A 无权接触的私人真实环境证据；
- **人类是授权者与裁决者**，定义结果、控制权限，并决定价值取舍和剩余风险。

“80% 以上”是资源分配方向，不要求记录工时或维护配额。判断标准是：只要任务不需要进入用户授权的私人真实环境，就继续由 A 完成；B 的工作面必须始终比 A 窄。

这是一套任务判断方法，不是 Agent 控制面。不得据此建立固定生命周期、Agent 注册表、平行任务板、治理脚本或强制报告体系。一般人机责任仍遵循[人机协作原则](agent-execution.md)，证据要求遵循[软件可信验证原则](trusted-verification.md)。

## 1. 三个角色分别负责什么

### Agent A：主力交付 Agent

A 默认拥有一个纵向用户结果，而不是只接收分散的编码步骤。A 负责：

1. 理解人的业务目标、成功标准、非范围和产品约束；
2. 搜索现有事实、源码、消费者、真实运行证据与可复用实现；
3. 完成业务分析、方案设计、代码、文档、迁移和 UI；
4. 依据已确认的真实来源语义实现状态转换，不用人工 fixture、Mock 或自设 Oracle 替代来源事实；
5. 运行静态检查、类型检查和构建来发现实现问题，并在目标真实环境中完成实际操作验收；
6. 根据失败修复实现，不把失败改写成成功；
7. 向人说明已完成结果、直接证据、未覆盖范围和 unknown；
8. 必要时提出一个精确的“授权证据缺口”。

A 不得：

- 把普通开发、静态排错或不涉及授权环境的实现工作推给 B；
- 仅因任务复杂、风险高或状态多就启用 B；
- 访问真实账户、真实资产或交易、Cookie、Token、Raw Snapshot、登录态或完整 Network Logs；
- 根据模拟、静态或构建结果猜测真实来源一定兼容；
- 把需要人决定的目标、风险承受或授权范围交给另一个 Agent 决定。

A 的停止条件是：继续工作必须猜测真实私人来源语义、越过授权边界、执行不可逆操作，或改变人的目标和风险取舍。此时应保留 `BLOCKED/UNKNOWN`，而不是自行扩大范围。

### Agent B：授权真实环境验证 Agent

B 不是 A 的通用 reviewer、第二开发者或质量兜底。B 只验证一个经过人明确授权的真实环境问题，例如：

- 登录后某字段是否存在、方向和时点是什么；
- 私人来源是否区分申请、部分确认和最终确认；
- 实际分页 Coverage 是否完整；
- 真实同步链路、持久化或 reload 是否按契约发生；
- 目标真实环境是否暴露了不应暴露的敏感信息。

B 不得：

- 设计或修改 Core 产品规则；
- 判断用户的投资、健康、职业或其他私人决策是否合理；
- 重做 A 的需求分析、实现、静态检查或构建；
- 创建、修改或删除真实用户数据；
- 执行买入、卖出、申购、赎回、调仓、转账或其他账户操作；
- 扩大人批准的页面、字段、时间窗、动作或数据范围；
- 把原始私人数据复制到仓库、fixture、摘要或长期记录。

只要授权不明确、环境不匹配、页面要求修改真实状态、敏感信息无法隔离，或结论只能靠猜，B 必须停止并返回 `BLOCKED/UNKNOWN`。

### 人类：授权者与裁决者

人负责：

- 定义想改善的人的结果和可接受的完成标准；
- 决定是否允许 B 进入真实私人环境；
- 限定目标、环境、数据、动作、持续时间和停止条件；
- 批准不可逆、对外或用户可见的高风险行为；
- 处理证据冲突、价值取舍和剩余风险；
- 以真实用户任务进行最终产品验收。

人不需要替 A 搜索代码、拼装 Agent 报告或重复机械测试。B 的存在也不意味着人已默认授权；每次进入真实私人环境都需要与当前问题匹配的明确授权。

## 2. 什么时候才启用 Agent B

只有以下五项**同时满足**时才启用 B：

1. **A 已完成可完成部分**：源码、契约、Core 和静态排错已经完成或明确报告失败，并已列出必须由目标真实环境验证的主张；
2. **主张可验证**：剩余问题被写成一个可观察、可判定的具体主张，而不是“帮我全面看看”；
3. **确有权限缺口**：该主张只能由真实登录环境、私人数据、本机状态或用户特定权限证明；
4. **人明确授权**：人批准目标环境、允许观察的数据、允许动作和停止条件；
5. **可最小化暴露**：B 可以只读完成，并只回传不能还原用户私人事实的结论。

以下情况**不启用 B**：

- Markdown、需求整理、普通 UI、Core 公式或状态机；
- migration、类型检查、构建和其他静态排错；
- 可在目标真实公开环境完成的来源操作；
- 只是希望再找一个 Agent 重看代码；
- 还没写清楚用户目标、Oracle 或完成主张；
- 真实验证必须创建交易或改变用户数据。

可信验证并不等于必须使用 B。独立需求、公式、参考实现、反例、Property 和 Invariant 仍然是可信 Oracle，通常由 A 在非私人环境内完成。B 只填补**权限隔离造成的真实环境证据缺口**。

## 3. 最小协作闭环

```text
人定义目标与默认隐私边界
→ Agent A 完成分析、实现与静态排错
→ A 声明完成证据和仍存在的授权证据缺口
→ 没有缺口：直接交人完成任务验收
→ 存在缺口：人决定是否授权 B
→ Agent B 在最小真实环境范围内只读验证并脱敏回传
→ Agent A 根据结论修复实现或更新状态
→ 仍需真实证明且人再次授权时，B 只定点复验受影响主张
→ 人裁决最终价值、unknown 与剩余风险
```

不得把它机械变成每项任务的固定流程。多数任务应在 A 完成后直接进入人的验收；没有授权证据缺口时，不创建 B 步骤。

## 4. 人需要看到什么

协作信息应附着在当前产品工作包、PR、对话或人类审查正文中，不另建 A/B 两套任务板。

A 交付时最少说明：

- **人的目标**：本次改善哪个用户任务或判断；
- **完成结果**：代码和产品现在可以做什么；
- **证据**：目标真实环境中的哪些实际操作直接支持哪些主张；
- **边界**：明确非范围、失败、未验证和 unknown；
- **授权证据缺口**：是否存在，以及为什么 A 无权在目标真实环境证明；
- **人的决定**：只列真正需要授权、价值取舍或风险接受的事项。

这不是固定表单。内容简单时可压缩为几句话；只有存在真实环境缺口时才增加 B 的授权信息。

## 5. 怎样申请一次 B 验证

A 必须先把请求收敛为：

- 待验证的具体主张；
- 主张对应的用户结果；
- 已有源码检查、构建结果和真实公开环境事实；
- 为什么这些材料仍不能证明目标私人环境；
- 需要进入的真实环境与目标能力；
- 允许观察的字段或行为；
- 明确禁止观察、保存和输出的敏感内容；
- 只读步骤和停止条件；
- 期望的脱敏结果，以及结果怎样影响 A 的实现。

人只批准当前请求。对一个字段、页面或来源的授权，不自动扩展到其他账户、时间窗、Network 请求或后续复验。

## 6. B 怎样回传而不泄露数据

通用回传只包含完成裁决所需的最小信息：

```text
Task
Authorization
Environment
Result: PASS | FAIL | BLOCKED
Target capability
Observed capability or field presence/absence
Field semantics
Coverage
Unknown
Required change
Sensitive data exposed
Stopped because
Agent A dependency impact
```

领域可以进一步收紧，不得放宽人的授权。B 不输出可识别个人的名称、金额、收益、日期金额组合、Raw JSON/HTML、Cookie、Token、银行卡信息、登录态或完整 Network Logs。原始材料只在授权会话临时观察，不进入仓库、fixture、摘要或长期记忆。

`PASS` 只证明授权步骤和环境中直接观察到的主张；`FAIL` 表示结果与既定 Oracle 不符；`BLOCKED` 表示无法在授权和安全边界内取得证据。未观察到的范围保持 `UNKNOWN`，不得并入 PASS。

## 7. B 返回失败后怎样修复

```text
B 返回脱敏 FAIL / Required change
→ A 依据已观察的来源事实修复代码或契约
→ A 用静态检查和构建排除实现错误，但不据此宣称完成
→ 人决定是否再次授权 B 在同一目标真实环境定点复验
→ 只有真实操作结果符合预期后才能通过验收
```

A 不得要求 B 提供原始私人数据以方便调试。B 不直接携带真实数据开发，也不通过修改 Oracle、忽略 Coverage 或扩大“成功”含义来消除失败。

事实冲突先比较要求、Oracle、环境和客观证据；只有目标、授权或风险取舍冲突才交给人。无法消除的冲突保留为已知限制或 `UNKNOWN`，不无限循环调用 Agent。

## 8. 在产品工作包中怎样表达

产品资料第一层始终按用户结果组织。每个纵向工作包可以内嵌：

- **A 主交付**：为这个用户结果完成哪些产品、Core、UI 和静态排错；
- **授权证据缺口**：当前是否确实存在；
- **B 窄验证**：仅当缺口存在且获授权时验证什么；
- **人的验收**：用户能否理解结果、证据、限制和下一步。

不要按 Agent 名称拆产品导航，不建立 Agent A backlog 与 Agent B backlog，也不要让维护者跨多个报告拼接当前状态。产品信息组织继续遵循[产品设计标准](product-design.md)，需求与技术是否匹配遵循[业务任务分析执行规范](business-task-analysis.md)。

## 9. 首个领域实例

Investment Review 是本标准的首个应用：

- Agent A 使用源码和已确认的来源语义负责 Core、迁移、状态机与 UI；静态检查只用于排错；
- Agent B 仅在维护者明确授权后，验证真实登录 Chrome 中的天天基金来源字段、语义、Coverage 和同步链路；
- 维护者定义投资范围和个人规则，批准真实环境访问，并完成人的基金复盘验收。

其金融、隐私、真实 Chrome 和禁止自动交易的加严边界，以[Investment Review 人的产品审查](../product/investment-review.md)和[工程附录](../product/reference/investment-review-engineering.md)为准。该实例不能反向推出所有产品都需要真实环境 Agent B。

## 10. 失效信号

出现以下任一情况，应停止或简化这套协作：

- B 成为每个复杂任务的默认 reviewer；
- A 把本应自己完成的实现或静态排错交给 B；
- B 的任务范围接近或超过 A；
- 人需要维护独立任务板、固定报告、Agent 注册表或完整生命周期；
- 私人原始材料开始进入仓库、fixture 或长期记录；
- Agent 调用增加，但共同假设、返工或人的整合成本没有下降；
- 人看见了 Agent 状态，却更难理解产品是否解决自己的问题。

资源是否有效，最终看是否减少隐私暴露、自证错误、重复劳动和人的判断成本，而不是调用了多少 Agent。
