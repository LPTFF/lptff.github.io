# 业务任务分析执行规范

这份文件是 [Agent 业务任务分析协议](../theories/agent-business-task-analysis.md) 经过项目判断后形成的最小执行规范，不是理论原文的替代品。理论卡片记录来源、理论主张、项目综合、适用边界、未知和复评条件；本文件只规定当前项目已经采纳、会影响 Agent 与产品判断的部分。不得借理论名称静默增加强制流程。

本规范用于降低业务目的、用户任务、信息表示和技术实现之间的错配。它与[可信验证执行规范](trusted-verification.md)互补：本规范帮助判断“什么结果值得实现”，可信验证帮助判断“证据是否足以说明该结果已经实现”。

## 1. 功能名称先视为候选手段

面对非简单产品或软件需求，不要自动把“导出、搜索、筛选、仪表盘、大表格、接口、缓存、AI 分析”等被点名能力解释为业务目的或用户任务。

先结合已有需求、产品资料、代码消费者和使用证据判断：

- 用户最终要完成什么任务；
- 用户需要回答什么问题或作出什么判断；
- 被点名的能力为什么可能有用；
- 能力交付后，用户还要完成哪些关键工作。

如果原始要求已经明确了任务、上下文和成功标准，可以直接使用这些信息，不要为了遵循规范重复询问已知事实。

## 2. 至少建立一层 WHY 和一层 HOW

重要需求至少能回答：

- **向上 WHY**：这项能力支持什么任务、判断、目的或系统约束？
- **向下 HOW**：已确认的任务和判断将由什么信息、加工、表示、技术及实现支持？

需要完整分析时使用以下链路：

```text
业务目的 / 系统约束
  → 用户任务
  → 问题 / 判断 / 决策
  → 所需信息
  → 信息获取与加工
  → 信息表示
  → 技术能力
  → UI / API / 数据
  → 代码
```

代码节点应能向上追溯 WHY；已确认目标应能向下说明 HOW。链路用于发现断点，不要求每个节点都写成单独文档。

## 3. 不知道就保留未知

业务目的、用户任务、使用情境或必要信息没有证据时：

- 明确写 `unknown`、待确认或缺失链路；
- 说明现有证据实际支持到哪一层；
- 区分需求原文、项目事实、代码推断和 Agent 假设；
- 只有该未知会改变范围、风险或方案时，才请求维护者决策。

不得为了让业务图完整而发明目的，也不得把代码当前行为反向解释成它必然正确表达了业务目标。

## 4. 判断 Task–Technology Fit

对重要方案说明技术能力与目标任务的匹配度：

- **HIGH**：直接降低目标任务的主要成本；
- **MEDIUM**：解决必要中间步骤，仍留下重要人工工作；
- **LOW**：技术可以运行，但多数关键工作仍由用户承担；
- **UNKNOWN**：任务或使用证据不足，无法判断。

等级必须附理由。重点检查：用户收到什么、用户实际需要什么，以及两者之间还剩哪些搜索、加工、比较、推理和行动。

不能因实现可行、响应更快、数据更多或文件可下载，就自动判断为高匹配。

## 5. 信息密集型功能必须检查总任务成本

以下功能默认触发加强分析：搜索、列表、筛选、报表、仪表盘、Excel/CSV、日志、BI、大表格、统计和监控。其他功能如果主要价值依赖用户从大量信息中形成判断，也按本节处理。

至少检查：

1. 用户最终要回答的问题或作出的判断；
2. 判断真正需要的信息量与系统暴露的信息量；
3. **访问成本**：入口、权限、等待和页面跳转；
4. **搜索成本**：查询、过滤、翻页和浏览；
5. **识别成本**：发现相关项、状态、模式和异常；
6. **加工成本**：清洗、聚合、计算和转换；
7. **比较与推理成本**：跨对象、时间和方案形成结论；
8. 用户得到结论后如何采取行动或进入反馈闭环。

明确区分：

- 取数或检索是否更快；
- 完成整个任务是否更容易。

局部效率提升不能替代总任务改善证据。

## 6. 检查信息表示是否支持目标操作

同一数据可以用原始记录、表格、导出文件、分组汇总、趋势、异常列表或其他方式表示。选择表示前，先确认用户需要哪些操作：

- **search**：定位目标；
- **recognition**：识别类别、状态、模式或异常；
- **comparison**：比较对象、时间或方案；
- **inference**：得到任务相关结论。

数据字段齐全不等于表示适合任务。若用户必须在系统外重建结构或进行大量人工运算，应将其记录为 representation mismatch 或 outcome gap，而不是把数据可获得当作任务已完成。

## 7. 导出、报表与大表格按任务判断

不按数据量或组件类型一概判断方案优劣：

- 归档、审计留存、完整交换等任务需要全量记录时，原始导出可能是高匹配方案；
- 异常识别、趋势判断、对比决策等任务需要加工和推理时，只提供全量原始数据通常只解决中间步骤。

验收必须覆盖目标任务。如果任务是异常识别，导出成功、行数正确和文件可打开只证明数据交付，不证明用户已经更容易识别异常。

## 8. 只在必要时显式输出完整分析

以下情况适合使用业务图、表格或理论卡片中的可选 YAML：

- 目的、任务和被请求能力可能错配；
- 方案会影响产品范围、数据、隐私、外部行为或较大投入；
- 信息密集型功能把大量认知工作留给用户；
- 多个方案在检索成本和总任务成本上有明显差异；
- 发现关键链路缺失，需要维护者作出产品取舍；
- 分析结果值得作为后续设计、实施或验收依据保留。

以下情况通常不需要完整结构：

- 拼写、文案和明确的局部样式修复；
- 目标、影响范围和验收标准已经清楚的小改动；
- 不会改变用户任务、信息结构或产品结果的机械调整。

即使触发分析，也只保留帮助判断的字段。不得为了模板完整而重复事实、制造未知答案或增加无后续价值的文档。

## 9. 与产品设计和可信验证衔接

产品设计时，分析结果应落实为：

- 主任务与成功结果；
- 必要信息、来源、新鲜度和隐私边界；
- 所需加工与表示；
- 主流程、失败状态、恢复路径和后续行动；
- 明确在本轮范围内解决的任务成本与保留的 outcome gap。

完成声明遵循[可信验证执行规范](trusted-verification.md)：

1. 把“用户能完成什么任务或判断”拆为可观察主张；
2. 为主张指定来自需求、业务规则、真实消费者或使用结果的可信 Oracle；
3. 在匹配的代码、浏览器、接口、数据或真实使用环境中取证；
4. 区分技术交付、局部效率改善和端到端任务改善；
5. 只报告证据实际覆盖的结果，剩余部分写明未验证、失败、无法验证或未知。

## Agent 的最小判断循环

面对复杂需求或产品方案，Agent 应按以下顺序判断，不需要机械生成固定模板：

1. 把被请求能力作为候选手段，识别已有目的、约束、任务和成功结果。
2. 至少向上追问一层 WHY、向下说明一层 HOW，记录关键缺失链路。
3. 明确用户要回答的问题、所需信息、加工与表示。
4. 说明 Task–Technology Fit 和能力交付后仍由用户承担的工作。
5. 对信息密集型功能检查访问、搜索、识别、加工、比较、推理和注意成本。
6. 选择最小、可撤销且直接支持任务的方案，不因现成组件或工具改变目标。
7. 用匹配目标任务的 Oracle 和真实证据验收，区分局部技术成功与用户结果。
8. 只有重要结构、取舍或未知值得保留时，才输出或沉淀完整分析。

核心判断是：**这项技术能力是否以可验证的方式降低了用户完成目标任务的主要成本，而不是功能是否已经存在。**
