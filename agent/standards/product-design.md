# 产品设计标准

## 产品方向

项目围绕“利用私人数据持续改善重要决策的个人高收益软件”演进。交易复盘是第一主线，职业资产和健康精力是后续候选；通用能力只在具体场景完成闭环后抽象。

产品闭环统一为：

> 记录 → 分析 → 改进 → 验证

决策记录统一关注：

> 目标 → 信息 → 判断 → 行动 → 预期 → 结果 → 错误归因 → 修改规则

当前产品组合和能力入口见[产品工作台](../product/README.md)。Investment Review 的用户问题、当前差距、P0–P4、分工和人的验收由[人的产品审查正文](../product/investment-review.md)统一负责。需求背后的目的、任务、信息与技术匹配分析遵循[业务任务分析执行规范](business-task-analysis.md)；高风险投资领域的 Measurement、Attribution、Appraisal 和行为研究边界见[投资绩效与决策复盘理论卡](../theories/investment-performance-and-decision-review.md)。本文件只定义跨产品设计方法，不把规划假设写成已实现能力。

## 设计顺序

1. 区分业务目的或系统约束、用户要完成的任务，以及需求中被点名的候选手段；证据不足的部分保留未知。
2. 明确用户需要回答的问题或作出的判断，以及成功结果。
3. 识别每个判断的最小数据、来源、隐私边界、新鲜度和必要的信息加工；一个判断的数据不足不能无理由阻断其他独立判断。
4. 将专业概念和工程依赖追溯到它实际支持的用户判断；不把最重、最完整的专业分析链误设为所有高价值任务的共同前置条件。
5. 选择支持目标任务的表示，检查搜索、识别、比较和推理是否仍需大量外部人工工作。
6. 判断技术能力与用户任务的 Task–Technology Fit，写明本轮降低的任务成本和仍保留的 outcome gap。
7. 设计主流程、空状态、失败状态、过期状态、恢复路径和后续行动。
8. 使用现有路由、数据消费者和 Element Plus 组件组合页面。
9. 只补充必要的业务 CSS，并验证桌面和移动端。
10. 为结果建立反馈或复盘入口，避免只做无后续行动的仪表盘。

不要求明确的小修机械输出完整业务图。只有目的、任务与方案可能错配，或重要链路缺失时，才将分析显式写入产品资料。

## 信息密集型功能

搜索、列表、筛选、报表、仪表盘、Excel/CSV、日志、BI、大表格、统计和监控不能只按“数据是否可见”设计。还要检查：

- 用户最终要回答的问题，以及真正需要的信息量；
- 系统暴露的信息量与无关信息；
- 访问、搜索、识别、加工、比较和推理成本；
- 表示是否帮助发现模式、差异、异常和可行动结论；
- 改动降低的是取数成本，还是完成整个判断的成本；
- 数据交付后，用户还要在系统内外完成哪些工作。

全量导出适合归档、审计留存或数据交换时可以是高匹配方案；若目标是发现异常或作出判断，应另外验证筛选、比较、计算和推理是否得到支持。

## 高风险领域与确定性边界

金融、健康、安全等高风险产品不能只套通用 UI 方法：必须先引入并核验领域理论，区分外部原始主张、项目工程约束和待验证产品假设。

Investment Review 固定采用：

```text
Normalized Facts + Coverage
→ deterministic Measurement / Rules / Attribution / Appraisal
→ structured Findings
→ optional AI explanation
```

- 核心数学、版本解析、规则违反和状态分类由确定性代码产生；
- AI 只解释、关联、提问和总结，不补数据、不预测、不改变状态；
- 更换或关闭 LLM 不得改变 metric、Finding 或 appraisal；
- 重要自然语言结论必须可下钻到 metric、transaction、decision 或 rule；
- 数据不足优先 `INSUFFICIENT_DATA`，不以更流畅文案掩盖缺口；
- 涉及投资时严格分离 Target/Benchmark、Process/Outcome 和 draft/真实执行。

## 人类可理解性与信息组织

产品和产品资料都必须扩展人的能力，不能把 Agent 的工作分解转嫁给人：

- 第一层按用户要完成的判断、流程和结果组织，不按 Agent、数据库对象、组件或团队角色组织；
- 每个专业概念都要能说明它帮助回答哪个问题；若只是把不适用概念藏起来，却没有修正错误的业务目的、任务顺序或依赖关系，仍视为产品逻辑未完成；
- 数据准备度按判断管理：显示这个问题缺什么、还能回答什么和怎样恢复，不以一份机构级全量清单作为所有用户进入产品的门槛；
- 高级或专业能力应在它所服务的问题出现时启用；不能让可独立完成的首要用户任务等待无关的 Benchmark、归因、跨币种或统计依赖；
- 当前需求、当前/目标差距、分工、状态和人工验收应在一个连续审查面中完成；
- Agent 分工是用户成果的内部实现信息，应附着在纵向工作包中，不成为用户界面或产品资料的第一层导航；
- 涉及私人真实环境时，纵向工作包先说明主力 Agent 的完整交付和证据；只有存在非私人环境无法证明的授权证据缺口时，才按[主力 Agent—授权验证 Agent—人类裁决者协作标准](main-agent-authorized-validation.md)内嵌窄范围验证与人的授权点，不建立平行 Agent 任务板；
- 采用渐进披露：先给普通语言结论、数据准备度和下一行动，再按需下钻公式、状态机、来源和工程证据；
- 新增文件、页面或抽象前，检查它是否减少访问、搜索、识别、比较和整合成本；只方便机器分类而增加人的跳转时不得采用；
- 用户不应需要理解 Agent 名称、任务 ID、canonical 对象或测试术语才能完成业务任务；这些内容只能作为可选追踪信息；
- 技术正确但人无法在合理时间内完成目标判断，产品验收失败。

## UI 与交互

- 默认遵循 Element Plus 的设计语言、主题变量和交互模式。
- 优先复用项目已有的独立功能布局、卡片、表格、表单、反馈、加载、分页和弹窗模式。
- 页面结构按“业务结构 → Element Plus 组件组合 → 少量业务样式”实现。
- 重要状态必须可见：无数据、加载中、来源失败、保留快照、数据过期、校验失败和权限阻断不能混为普通成功。
- 涉及分析或建议时，区分事实数据、推导结果、估算和风险披露。
- 涉及私人数据时默认本地优先；云同步、远程埋点和第三方上传需单独授权和风险评估。

## 产品验收

- 入口可发现，主流程可完成，错误后可恢复。
- 数据结构、来源、更新时间和消费者行为一致。
- 页面不以 HTTP 200、JSON 可解析或静态文件存在冒充业务成功。
- 桌面与相关移动视口无关键内容丢失或横向溢出。
- 网络和控制台无影响核心流程的错误。
- 用户能理解结果意味着什么、不能证明什么，以及下一步行动。
- 验收覆盖用户的目标任务或判断，而不只覆盖数据可见、文件可下载、接口成功或组件可操作。
- 能说明技术交付与用户最终需要之间的 outcome gap；若声称改善总任务效率，应有对应的真实使用证据。

详细证据等级和报告格式见[自测与验收手册](../verification/playbook.md)。
