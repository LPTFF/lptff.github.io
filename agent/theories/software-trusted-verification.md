# 软件可信验证原则

- **领域**：Verification & Validation、Independent V&V、软件测试、统计可靠性、形式化方法
- **状态**：理论收藏，执行边界已收敛
- **收藏日期**：2026-08-08
- **项目落地**：[可信验证执行规范](../standards/trusted-verification.md)

## 它试图解决什么问题

软件实现、开发者理解和真实运行行为之间可能存在偏差。构建成功、类型检查通过或测试全部通过，都只能证明它们直接覆盖的性质，不能自动证明页面可用、真实接口兼容、数据正确、用户流程成功或部署环境行为正确。

这套原则要求 Agent 让验证方法和证据环境匹配软件主张，并在证据不足时保留未知，而不是凭代码外观或工具绿色状态宣布完成。

## 理论主张

### Verification 与 Validation 不同

- **Verification**：软件是否按照规格被正确实现。
- **Validation**：软件在预期使用环境中是否真正满足用途和用户需求。

运行时要求应在相应运行环境中观察。浏览器行为需要浏览器验证，真实外部依赖需要集成或目标环境验证，部署要求需要观察目标或等价环境。

### 结论需要 Objective Evidence

重要结论应由可复查的客观证据支撑，例如静态分析、测试结果、真实执行、浏览器观测、接口响应、数据库状态、构建产物、运行日志或协议验证结果。证据只能支持其实际覆盖的范围。

### 测试需要可信 Oracle

测试必须有判断实际结果正确与否的依据。Oracle 可以来自正式规格、业务规则、数据约束、协议定义、领域不变量、可信参考实现或真实消费者的可观察结果。若 expected result 只是从当前实现推导，测试和实现可能共享错误假设。

### 高风险场景需要独立验证

开发与验证如果共享相同假设，可能共同遗漏同一错误。应根据风险引入独立测试设计、独立需求解释、不同验证方法、独立 Agent 或独立参考实现，以减少共同错误，而不是为了增加形式流程。

### 普遍规则应表达为 Property 或 Invariant

重复操作幂等、失败不破坏有效状态、集合型计算不受无关顺序影响、没有新证据时状态不能升级等规则，适合用 Property-Based Testing、状态模型或不变量表达，而不只是累积有限样例。

### 没有绝对输出时使用 Metamorphic Relation

当很难知道唯一正确输出时，可以验证输入变化与输出变化之间必须成立的关系，例如改变无关顺序不应改变顺序无关的结果，重复幂等操作不应改变最终状态。

### Mock 不能证明真实兼容

Mock 只说明内部逻辑在某个外部行为假设成立时如何运行。它不能证明第三方 API、浏览器、数据库、认证系统、文件系统、网络、CLI 或协议实现真的满足该假设，因此高风险外部依赖需要真实集成、契约测试或目标环境验证。

### 有限测试不能推出无限可靠性

“全部测试通过”只能描述有限样本、运行分布和覆盖场景。若需要统计可靠性结论，必须说明目标总体、样本生成方式、独立性假设、成功/失败定义、统计模型、置信水平和区间计算。缺少这些前提时，只报告观察结果和剩余未知。

### 复杂状态系统可以补充形式化方法

并发、分布式协议、同步、重试、事务、去重、一致性、恢复和权限状态转换，可能存在有限样例未覆盖的状态组合。可以用 `State / Action / Transition / Invariant` 建模并用 model checking 搜索反例。

形式化验证证明的是模型内部性质；真实运行验证还要确认模型、实现和外部世界相符，二者不能互相替代。

### 真实缺陷应转为回归证据

真实运行发现且能稳定复现的缺陷，应转化为回归测试、Property、Invariant、Contract Test 或其他可重复验证条件，并保留可信 Oracle 和复现条件。

## 当前项目采纳范围

当前项目只把以下边界转化为执行规范：

1. 项目验收的唯一完成依据，是目标真实环境中的实际操作结果符合人的预期。
2. 页面和浏览器扩展通常使用 Chrome DevTools MCP 接管用户实际 Chrome 验收；BOSS 直聘按项目专用手册使用普通 Chrome 与 OS 级桌面操作。不能取得对应目标环境证据时保持准确的失败、未验收或基础设施状态。
3. 源码阅读、构建、Mock、fixture、Oracle、Property、Metamorphic Relation、形式化模型和其他测试工具只能用于静态排错或理论分析，不能替代真实环境验收，也不能单独支持完成结论。
4. 证据不足时必须保留 `FAIL`、`BLOCKED`、“未验收”或“未知”，不得为了取得绿色结果建立替代测试体系。

本卡片其余内容用于保存理论来源、主张、适用条件和局限。它不自动产生项目测试要求，也不授权 Agent 创建或保留脱离真实环境的测试工具、Mock、fixture、Oracle、Property、Metamorphic Relation 或形式化验证方案。

## 适用边界与局限

- 这套原则不能替人确定产品目标、风险承受能力或验收标准。
- 它不能消除 Test Oracle Problem；没有可信 Oracle 的部分仍可能只能得到弱证据或未知。
- Property-Based Testing、Metamorphic Testing 和形式化验证不能替代真实环境 Validation。
- 独立 Agent 不天然独立；如果共享同一需求误读、数据和工具，仍可能产生共同错误。
- 统计可靠性结论依赖抽样、分布和独立性假设，不能由测试数量直接推导。
- 文档链接、静态检查和构建成功不能代替用户流程、外部兼容性或部署环境证据。

## 当前证据与未知

项目已经把真实环境验收边界写入执行规范；这只证明规范存在，不证明所有后续任务都会自动遵守，也不证明软件缺陷率必然下降。本卡片中未被执行规范采纳的方法继续作为理论资料保留。

仍需通过后续真实任务观察：

- Agent 是否更少把构建成功误报为真实可用。
- 记录“未知”和未覆盖范围是否改善人的决策，而不是增加无效文档负担。
- Chrome DevTools MCP 与其他目标真实环境操作是否覆盖了实际用户关键路径。

## 复评触发条件

出现以下情况时，应重新检查理论卡片和执行规范是否仍然适用：

- 项目新增真实外部依赖、复杂同步或高风险状态转换。
- 真实运行发现当前规范没有捕获的缺陷。
- 规范开始被机械执行，却没有改善证据质量或人的判断。
- 新证据显示某项方法成本过高、Oracle 不可靠或验证环境不匹配。
- 相关理论来源、标准或项目目标发生实质变化。
