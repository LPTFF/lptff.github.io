# 协作模型与沟通约定

## 1. 目的

本文定义与外部开发者交流时的公共语言：讨论可复用的方法、证据和边界，不交换公司内部项目资料。

## 2. 角色分工

| 角色 | 责任 |
| --- | --- |
| 内部项目维护者 | 在公司项目中验证问题，维护内部适配模板，决定是否提出公开改进 |
| 外部开发者 | 提供公开方法论、实现建议、兼容性信息或审查意见 |
| 脱敏审查人 | 检查个人信息、公司信息、客户信息、内部路径、凭据和业务机密是否泄露 |
| 技术审查人 | 判断改进是否准确、可复现、与目标开源项目兼容 |
| 发布审批人 | 确认公开发布范围、许可证、责任归属和上游提交方式 |

一个人可以承担多个角色，但脱敏和发布决定应保留可追溯记录。

## 3. 交流时提供什么

建议优先提供以下公共信息：

- 可公开的目标和问题描述；
- 与问题直接相关的最小代码或伪代码；
- 脱敏后的目录结构和接口边界；
- 预期行为、实际行为和复现步骤；
- 已运行的测试、检查命令及结果；
- 对兼容性、回滚和维护成本的影响判断；
- 希望外部开发者回答的问题。

## 4. 交流时不提供什么

除非已经完成正式授权和发布审批，不得提供：

- 公司名称、客户名称、内部项目名称、员工信息和工单编号；
- 内部域名、仓库地址、绝对路径、网络拓扑和部署地址；
- API 密钥、令牌、Cookie、私钥、访问链接和环境变量值；
- 真实业务数据、用户数据、日志原文和可识别的截图；
- 内部 Agent system prompt、权限规则、工具配置和组织级策略原文；
- 尚未公开的商业计划、供应商信息、漏洞细节或合规判断；
- 通过上下文组合即可推断出上述信息的细节。

需要说明背景时，使用“内部项目”“业务系统”“公开仓库”等中性表述，并只保留影响技术判断的部分。

## 5. 外部问题的最小格式

与外部开发者交流时，优先使用 [外部问题模板](templates/external-question.md)。问题应能独立阅读，不要求对方访问内部系统。若必须提供仓库，提供专门的脱敏复现仓库，而不是内部项目镜像。

## 6. 讨论结果的状态

每项外部反馈应标记为以下状态之一：

- **待确认**：已有建议，但尚未在项目或最小复现中验证；
- **已验证**：已有命令、测试或公开文档支持；
- **不采用**：说明不采用原因，例如不兼容、收益不足或超出范围；
- **待审批发布**：技术上可公开，但尚未完成发布审批；
- **已反哺**：已通过开源项目的文档、脚本或测试 PR 发布，并记录链接。

“外部开发者这样说”不能直接作为项目事实；只有完成受影响路径验证后，才可写入项目上下文。

## 7. 兼容性和责任边界

外部交流提供的是方法建议，不代表对公司内部系统的安全、合规、性能或生产可用性背书。内部项目维护者负责：

1. 验证建议是否适用于内部环境；
2. 评估依赖、权限、数据和部署影响；
3. 决定是否采用或形成公开改进；
4. 对最终合入和发布结果负责。
