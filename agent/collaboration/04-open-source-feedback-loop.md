# 开源反馈闭环

## 1. 开源项目的角色

开源项目是公开方法论、工具实现和社区反馈的来源。公司项目可以借鉴其设计，但不把公司内部模板视为上游项目的默认规范。

建议将外部反馈分成三类：

- **参考**：帮助理解问题，但不直接改变内部项目；
- **适配**：在公司项目中按权限、数据和构建环境调整后使用；
- **反哺**：经脱敏、审查和审批后，转化为组织无关的上游改进。

## 2. 从内部改进到上游贡献

```text
内部问题
  ↓
抽象为通用问题
  ↓
构造公开最小复现
  ↓
验证文档/脚本/测试改进
  ↓
脱敏与审批
  ↓
上游 Issue 或 PR
  ↓
跟踪反馈并回填内部决策
```

### 内部问题

记录原始问题、影响、受影响路径和内部验证结果，但不要把原始记录直接提交到外部项目。

### 抽象为通用问题

将“某公司某系统出现故障”改写为“在某种公开配置下，某工具产生某行为”。保留能够影响技术判断的约束，去掉组织背景和敏感细节。

### 公开最小复现

使用合成数据、临时目录、公开依赖和中性名称。最小复现应只保留触发问题所需的文件和命令。

### 验证改进

文档改进应检查链接、术语、示例和边界；脚本改进应检查输入、输出、错误处理、幂等性和安全默认值；测试改进应检查在公开 CI 环境中的稳定性。

## 3. 贡献类型选择

| 改进内容 | 首选交付 | 适用条件 |
| --- | --- | --- |
| 概念、边界、工作流 | 文档 PR | 不需要项目私有代码即可理解 |
| 可复用检查或同步逻辑 | 脱敏脚本 PR | 输入输出稳定、无内部服务依赖 |
| 可自动回归的行为 | 测试或 fixture PR | 能在公开 CI 中稳定运行 |
| 复杂或存在争议的方案 | 先提 Issue | 需要上游维护者确认方向 |
| 仅对公司系统有意义的适配 | 不公开 | 保留在内部模板或项目文档 |

## 4. 上游沟通原则

- 先描述可复现的技术现象，再描述建议；
- 引用公开文档和测试输出，不引用内部审查结论作为权威；
- 说明方案的兼容性、限制和未验证部分；
- 不要求上游接受公司内部流程或命名；
- 尊重上游项目的许可证、维护者决定和发布节奏；
- PR 只包含一个清晰主题，避免将内部清理事项混入通用改进。

## 5. 结果回填

上游反馈可能被接受、修改、拒绝或长期搁置。结果应回填到内部改进记录：

- **接受**：记录上游版本或 PR 链接，评估何时采用；
- **修改后接受**：记录上游最终方案与内部适配差异；
- **拒绝**：记录技术原因，不把内部方案继续描述为上游共识；
- **搁置**：保留未解决状态，避免在内部文档中写成已完成；
- **发现错误**：及时修订公开文档和内部上下文，并说明影响范围。

## 6. 成功标准

一次反哺不以“提交了 PR”为唯一完成条件。至少应满足：

1. 外部开发者可以在无内部访问权限的情况下理解问题；
2. 公开材料通过脱敏、技术和发布审批；
3. 文档、脚本或测试的验证证据可复核；
4. 上游反馈和内部后续责任已记录；
5. 没有把公司内部实现、数据或权限边界伪装成通用标准。
