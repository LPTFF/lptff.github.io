# 脱敏与发布审批

本文定义外部资料和开源 PR 的最低发布门槛。它是公开协作的流程建议，不替代公司法务、安全、隐私或出口管理制度。

## 1. 发布前检查单

### 身份与组织信息

- [ ] 删除公司、客户、团队、员工和内部项目名称；
- [ ] 删除工单号、会议链接、内部仓库地址和组织标识；
- [ ] 将绝对路径、域名、IP、集群名和账号名改为中性占位符；
- [ ] 检查截图、日志、提交信息和文件元数据是否包含身份信息。

### 凭据与安全信息

- [ ] 删除 API key、令牌、Cookie、私钥、密码、签名密钥和环境变量值；
- [ ] 删除可直接访问内部系统的命令、URL 和配置；
- [ ] 删除未公开漏洞、攻击路径、内部防护细节和安全事件信息；
- [ ] 确认占位符不会被误认为可用凭据；
- [ ] 对脚本执行路径、网络出口和文件权限进行安全审查。

### 数据与业务信息

- [ ] 真实用户数据已替换为合成数据；
- [ ] 删除交易、财务、客户行为、业务指标和内部策略细节；
- [ ] 删除能够通过多处字段组合重新识别个人或组织的信息；
- [ ] 将业务名称、数据字段和规则改写为通用示例，并保留足够的技术含义。

### 技术完整性

- [ ] 示例能够脱离公司内部上下文独立阅读；
- [ ] 命令、路径、配置和测试可以在公开环境中复现，或已明确标注为伪代码；
- [ ] 文档没有把推断写成事实；
- [ ] 兼容性、许可证、依赖和版本信息已由技术审查人确认；
- [ ] 脚本没有默认执行删除、发布、推送或其他不可逆操作。

## 2. 审批门槛

至少完成以下状态流转：

```text
草稿 → 脱敏审查 → 技术审查 → 发布审批 → 对外发布 → 结果回填
```

- **脱敏审查**：确认公开材料不含受保护信息；
- **技术审查**：确认示例正确、边界清晰、可以维护；
- **发布审批**：确认发布范围、许可证、归属、目标项目和发布方式；
- **对外发布**：创建文档或脚本 PR，保留公开链接；
- **结果回填**：记录 PR 状态、审查意见、后续修改和是否需要同步内部实践。

若任一检查项无法确认，应暂停发布，而不是用“应该没有问题”替代证据。

## 3. 改进的公开化步骤

1. 从内部问题中提炼技术问题，不复制内部文档原文；
2. 删除组织、项目、客户和数据语境；
3. 用合成示例重写问题、方案和验证；
4. 确认改进具有跨项目适用性；
5. 运行公开项目规定的测试、文档检查和安全检查；
6. 在 [开源 PR 交接模板](templates/upstream-pr.md) 中填写审查记录；
7. 完成审批后再创建或更新上游 PR。

## 4. 常见错误

- 把内部 `CLAUDE.md`、Agent prompt 或权限配置直接复制到公开仓库；
- 只删除 API key，却保留内部域名、路径和真实业务数据；
- 用公司真实日志作为“最小复现”；
- 因为改进来自真实项目，就默认它适用于所有项目；
- 没有运行测试就把脚本称为“已验证”；
- 将“内部采用”误写成“上游推荐”；
- 在 PR 描述中解释内部背景，导致正文、截图或历史记录重新泄露信息。

## 5. 审批记录的最小内容

审批记录不需要公开，但应能回答：

- 审查了哪一个具体版本或提交；
- 检查了哪些信息类别；
- 谁完成了脱敏、技术和发布确认；
- 哪些内容被删除或改写；
- 公开发布到哪个项目、路径或 PR；
- 发布后发现问题时如何撤回、修订或通知。
