# 产品工作台

这里首先帮助人理解产品，而不是展示 Agent 的文件组织。当前产品价值、边界和验收应在一次主文档阅读中完成；工程细节按需下钻，不作为理解产品的前置条件。

## 持续回答的产品问题

**现有工具能否以可承受的成本满足个人需要，哪些劳动可以交给工具和社会服务，哪些判断与恢复能力需要留在自己手里？**

项目通过功能的新增、维护和真实使用持续回答这个问题。现有投资复盘、资讯与福利筛选、导航、知识资产和娱乐已经在承担其中不同的作用；这些作用需要在使用中继续检验，不因功能存在就认定价值已被证明，也不因概念上缺少某个模块就另建一套管理系统。

“智力外包、决策保留”是主要分工：在授权与可信边界内，让工具和社会服务承担获取、整理、计算、比较、分析及可观察结果的追踪；人保留目标、重要代价的取舍、授权、否决与更换方案的能力。“最小”关注人长期需要亲自承担的劳动、注意力、维护与依赖成本，同时保有必要的理解和恢复能力，不能用页面或功能数量衡量。

项目不能以持续获得顶尖付费模型为前提。模型不可用时，允许分析深度和开发速度下降，或减少、暂停辅助能力，但不应阻断可独立运行的核心功能，也不应把全部任务转回用户手工承担。功能复杂度以长期可承受的理解和维护成本为界；这些是设计要求，是否满足仍需对应验证。

这是一项持续的产品判断，不是新的功能需求或固定路线图。具体需要可以支持新增功能；维护也可以选择简化、合并、替换或退出。完成一次工具任务、获得休闲体验、确认当前无需处理，都可以是有效结果，不要求每次使用再填写记录或复盘表。

## 当前维护方向

**2026-09-10 用户判断：现有功能基本满足需要，当前整理维护资料，不新增资源管理功能。** 上一次讨论中的“近期用途 → 候选比较 → 结果记录”方案不再作为待执行任务。

站点服务个人的信息获取、资源发现、职业机会、知识复用、投资复盘和休闲需要。各部分按真实需求维护，不设全站唯一产品主线，也不要求一个领域完成固定次数的使用验证后其他领域才能改进。Investment Review 文档中的 P0–P4 只表示该领域的设计阶段，不是全站任务排序。

“降低未来交易成本和脆弱性”用于理解已有功能的价值，不要求新增资源台账、任务中心、收入指标或统一复盘引擎。能找到入口、获得有用信息、完成一次工具操作、获得休闲体验，或判断无需行动，都可以满足相应需要。发现优惠不等于拥有资源，保存记录不等于形成产出；这些边界也不构成强制补建功能的理由。

## 需求验证与埋点监控规划（2026-09-13）

**状态：产品目标与技术方案规划，未实现、未测试。用户指定由 Antigravity 负责执行和测试。** 本节是本次需求的唯一规划入口，不表示已开启采集或已证明功能价值，也不将前文讨论中的资源台账、求职管理或收益管理自动列为建设任务。

### 产品目标与判断边界

用现有功能的真实使用证据，辅助决定保留、优化、合并、替换或暂停投入。重点观察职业机会、优惠支付和项目运行资源发现是否服务实际需要，同时保留知识复用、休闲及低频关键能力的独立价值。评价包含时间、现金、注意力、维护和权限暴露成本，不以访问量或停留越久越好为目标。

分别回答两件事：

- **是否刚需**：需要出现时，不具备该能力是否明显阻碍任务，替代方法是否代价较高。行为数据只能提供线索，需结合用户已有反馈；不得从点击次数自动宣布刚需。
- **是否长期需要**：是否跨多个相关周期再次完成有价值的任务。求职期、续费期和偶发恢复需求不适合用每日活跃衡量；需求阶段结束也不等于功能永久失效。

默认按最近 28 天观察、最近 84 天比较，均为首版可调整的观察窗口，不是行业标准或淘汰门槛。低频需求应等实际相关周期出现再判断。数据不足、关闭采集、未覆盖、存储被清理和功能不可用都必须显式标明，不能写成零需求。

| 观察现象 | 可支持的判断 | 后续取舍 |
| --- | --- | --- |
| 跨周或相关周期重复完成关键动作，并有有用反馈 | 持续价值的候选证据 | 优先维护可靠性，按具体阻碍优化 |
| 使用少，但真实需要出现时完成关键任务，替代成本高 | 低频关键能力的候选证据 | 保留易用入口，不因低活跃删除 |
| 常进入或尝试，但失败、无结果较多 | 可能有需求，交付存在阻碍 | 先排查数据、交互与运行问题 |
| 常浏览或外跳，但没有后续结果证据 | 存在信息消费，实际收益未知 | 保持现有边界，不夸大为收入或省钱 |
| 可靠可用、相关需要出现，但持续不用且用户确认替代方案更好 | 当前投入价值较低 | 考虑合并、替换或暂停；由人决定 |
| 刚上线、观察期短或采集覆盖不明 | 证据不足 | 保留 unknown，不自动评分、排名或删功能 |

### 最小观察链与事件语义

按功能观察“可用 → 可见 → 主动尝试 → 可观察完成 → 后续再用”，不要求所有功能套同一漏斗。功能入口曝光不等于功能内容可见；后台加载、预取、轮播和自动刷新不算主动使用。首页栏目在内部切换，不能仅靠路由统计。

| 事件 | 触发与含义 |
| --- | --- |
| `feature_view` | 页面处于前台且功能内容实际展示后计一次；相同功能每会话最多一次，用于观察可见会话数 |
| `task_start` | 用户主动触发预先登记的关键任务；生成一次操作标识，重复渲染不重新开始 |
| `task_result` | 同一次操作至多一个终态：`success`、`empty`、`failure` 或 `cancelled`；成功须来自消费者实际获得结果的回调，不能仅凭点击或 HTTP 200 |
| `outbound_open` | 用户触发打开外部资源，只证明外跳意图；不证明目标打开成功、投递、面试、领取或省钱 |
| `value_feedback` | 可选反馈：有帮助、无帮助、当前不需要；可附“缺少它是否阻碍任务”的枚举回答，不收自由文本，不强制弹窗 |
| `feature_health` | 沿用已有状态形成可用、过期、空数据、失败、未知等健康摘要；健康事件不计入人的活跃或需求 |

连续 30 分钟无主动交互后，新交互开始新会话；会话规则版本化。浏览器关闭或崩溃而无终态的操作显示为“未观察到结果”，不自动当作失败或取消。任务重试属于新尝试，但一次操作重复回调必须去重。首版不采集逐次点击流、鼠标轨迹或阅读时长。

首版关键动作映射由 Antigravity 在对应源码消费者处核对后实现：

| 现有功能 | 首版观察动作与完成边界 |
| --- | --- |
| 求职机会页 | 主动筛选或生成方向；有效结果展示才算对应任务完成。打开招聘平台单独计外跳；不观察简历、岗位文本、聊天或自动投递，不修改 BOSS 扩展 |
| 福利与资源发现 | 主动筛选，区分有结果与空结果；原文外跳只记录类别。银行卡、AI、VPS、域名、托管等采用固定类别，未知归其他；不记录标题与具体链接 |
| 导航 | 主动打开分类入口；复用现有本机计数逻辑的触发点，避免两套重复监听；历史累计计数不能还原为历史会话或回访 |
| 开发工具 | 用户主动运行后的可用结果或明确失败；不记录输入、输出、文件名和剪贴板内容 |
| 博客与娱乐 | 可见、主动操作或外跳及可选有用反馈；不声称阅读完成或强求变现，不以滚动到底作为价值证明 |

Investment Review、Contract Review 及浏览器扩展不纳入首批新增采集；通用路由钩子必须显式排除这些区域。后续如要观察，先补充对应领域边界，不能全站自动捕获。

### 分析输出与计算口径

仅需一个本机“功能使用”摘要入口，包含观察区间、采集状态、覆盖起点、功能版本、样本计数、最近有效使用日期和已知限制。不建设新的业务管理后台，不自动生成 AI 价值评分。

- **尝试比例**：有主动尝试的可见会话数 / 可见会话数；外跳类功能可用有外跳的可见会话数单独计算，不能混用操作次数作分子。分母为零显示不适用。
- **任务完成情况**：分别显示成功、空结果、失败、取消、无终态的次数；成功数 / 尝试数与终态覆盖比例一起呈现。跨日结果归属于操作开始日，无法关联的结果单独标记，不补造尝试。
- **持续使用**：有关键动作的不同自然日数、不同周数、相邻使用间隔及完成任务的周数。只代表此浏览器，不能命名为用户留存率或推算全站用户数。
- **价值反馈**：各反馈原始计数及反馈覆盖率，明确来自自愿反馈。无反馈是未知，不等于无价值；现金与节省时间不自动估算。
- **运行阻碍**：失败类别、空结果次数、数据新鲜度状态与未完成操作并列展示，辅助区分需求不足和能力不可用。无可靠健康证据时写未知。

先呈现事实和限制，再给出待核实的解释。版本变更、需要所处阶段、采集空窗和人工测试可能影响比较；不能从前后差异直接认定改版有效。默认排除开发、预览与自动化测试样本；无法可靠识别时必须使用显式测试模式隔离，不依赖声称能准确识别机器人。

### 技术方案与隐私边界

当前检查依据为 `src/main.js`、`src/router/index.js`、产品能力清单及定向搜索；未发现可直接复用的统一需求分析埋点入口，不据此声称全仓没有任何统计。已有导航本机点击统计，需实施时核对具体存储和消费者。

建议数据流：**登记的业务触发点 → 类型化事件校验与去重 → 独立本机 IndexedDB → 确定性聚合 → 本机摘要**。首版无后端、无远程上报、无第三方统计 SDK、无新增账号与付费服务、无定时 AI 调用。AI 可在以后分析用户主动提供的脱敏摘要，不作为统计运行依赖。

1. 在 `src/` 内建立独立的小型观察模块，按既有目录规范落位；包含功能及动作白名单、记录入口、存储、聚合与设置。运行代码不读取本规划文档。路由只辅助识别页面，栏目可见和任务完成由消费者显式触发。
2. 默认关闭记录，由本人在本机设置中开启；清楚说明只分析当前浏览器。提供暂停、清空和主动导出聚合摘要。清空须同时删除原始事件、聚合、会话及待写队列，重新开启时显示新的覆盖起点。
3. 只允许固定功能、动作、结果、错误类别、契约版本、功能版本、当地日期与时间区间等字段，以及去重所需的随机事件/操作/会话标识。标识只保存在本机，不生成永久访客 ID，不跨设备关联；清理或过期后不复原身份。
4. 禁止通用属性字典、DOM 文本自动采集、完整 URL、查询参数、搜索词、来源页、IP、设备指纹、账号、密钥、金融数据、简历和聊天内容。错误只映射固定类别，不存原始异常信息、堆栈或响应体；未知字段直接丢弃。
5. 默认原始事件保留 28 天、无标识的每日聚合保留 180 天；84 天趋势从日聚合读取。聚合在清理原始事件前幂等更新，窗口外完成的操作或缺失关联显示覆盖限制。每日去重与会话计数在标识仍存在时计算，禁止事后简单累加操作次数冒充会话数。
6. 首版设原始事件上限 20,000 条与存储预算目标 5 MB（实施时验证实际开销）；超限先保留可用聚合再清理旧事件，记录覆盖截断标记。存储不可用、超额、迁移失败或记录错误均静默降级，不能阻断核心功能，也不能循环记录自身错误。
7. 使用异步小批量写入；跨标签页通过事务保证事件去重和聚合幂等。持久化日期按记录时本地日界，保存时区偏移；切换时区标注不可直接比较，不回写历史日期。不依赖关页瞬间必定写入，丢失尾部事件属于覆盖限制。
8. 本机存储仍可能被同源脚本访问，不宣称绝对匿名或绝对安全；通过最少字段、保留期限和清空降低暴露。导出只包含固定字段聚合与覆盖说明，不含随机标识或原始事件。远程统计或跨设备同步不在本次范围。

### 交给 Antigravity 的实施与验收

按“基础模块与开关 → 首批消费者接入 → 本机摘要 → 验收”的顺序实现。先核对现有事件触发点与功能结果语义，无法可靠识别成功的动作只记录尝试或外跳。不要为埋点增加业务录入、权限、招聘外发或模型请求，不扩建资源台账；保留其他领域的现有边界。

以下是待执行的验收要求，不是已通过的测试：

| 验收场景 | 必须观察的结果 |
| --- | --- |
| 默认关闭、开启、暂停、清空、再次开启 | 关闭时无采集写入；暂停不新增；清空不被待写队列恢复；覆盖起点重置，核心功能正常 |
| 首页栏目切换、刷新、后台标签、重复渲染 | 只有前台真实展示计可见；同会话同功能去重；程序加载不算主动使用 |
| 成功、空结果、失败、取消、重试、关闭页面 | 终态与真实消费者一致；一次操作不会重复成功；无终态单列，重试可区分 |
| 多标签页、跨日、会话超时、版本或时区变化 | 无重复累计；跨日归属与聚合可解释；可比较范围和限制明确 |
| 存储被禁、额度耗尽、数据损坏、事件上限及过期清理 | 主任务仍可用；不产生错误循环；聚合不重复且显示采集缺口 |
| 敏感参数、输入、异常及未登记字段 | 原始存储和导出均无敏感内容；金融页与扩展不被通用钩子采集 |
| 网络与权限 | 开启记录及查看摘要不新增远程请求、账号权限或第三方脚本 |
| 已知小样本：2 个可见会话，1 个会话尝试 3 次，1 成功、1 失败、1 无终态 | 尝试比例为 1/2；任务成功为 1/3，终态覆盖为 2/3；不混淆会话和操作 |
| 无数据、短观察期、仅测试数据、主动导出 | 显示未知或不足；测试样本隔离；导出为脱敏聚合，不产生刚需结论 |

执行者按根目录 AGENTS.md 和真实环境验收原则，在真实 Chrome 完成相关交互与隐私检查；交付变更文件、测试结果、真实页面证据、可审查现场以及未验证范围。当前阶段只验证记录与分析是否可信；刚需和长期价值需上线后的真实使用与用户反馈，不能由构建、测试样本或一次演示证明。是否保留或退出功能最终由用户判断，不自动删除或停用。

## 产品判断规则

功能新增、维护和使用反馈，按当前问题的重要程度关注：

1. 这项功能支持人的什么需要，用户最终要完成什么任务、判断或体验；
2. 所需私人或外部数据是什么，来源与删除边界是否清楚；
3. 哪些劳动由系统或社会服务承担，哪些选择与必要能力仍由本人掌握；
4. 节省了哪些工作，又增加了哪些输入、阅读、切换、核查、维护或依赖成本；
5. 用户是否能理解结果意味着什么、不能证明什么、下一步是什么；
6. 用户反馈和对应使用结果是否支持保留、优化、合并、替换或退出；不设跨领域统一使用次数门槛。

这些问题由维护者结合已有上下文和使用反馈回答，不新增强制报告、打分表或用户填写流程。缺字段、长期未访问或没有新记录，本身不构成要求用户处理的现实问题。

用户确认“已满足需要”足以支持当前维护取舍，不要求先提供量化收益。它不等于每条技术路径都已验收；声称修复成功仍需匹配的真实证据，声称长期节省或收入改善仍需相应使用结果。

需求分析遵循[业务任务分析执行规范](../standards/business-task-analysis.md)，页面和交互遵循[产品设计标准](../standards/product-design.md)。功能名称只是候选手段；证据不足时保留 unknown，不为文档完整性虚构目的。

## 冲突时相信什么

```text
真实运行与匹配的可信验证
→ 当前源码
→ 活动产品正文中的 Current State
→ 目标产品与工程契约
→ source / archive 历史资料
```

下层事实可以否证上层规划。PRD、Mock、构建成功、HTTP 200 或页面出现都不能单独把能力升级为已实现。

## 资料边界

- [investment-review.md](investment-review.md)：投资领域的需求、事实、状态和验收入口，不代表全站方向。

- [reference/site-capability-inventory.md](reference/site-capability-inventory.md)：基于源码的站点级能力清单，不描述未来规划。

- [archive/](archive/)：已被替代的 PRD 和文档体系，不参与当前任务解析。
