## 1. 这是什么产品

Investment Review 是个人 A 股公募基金的**纪律与学习工具**，不是机构绩效系统的缩小版，也不是收益看板或 AI 买卖建议。

它首先帮助用户回答五个反复出现的问题：

1. 数据足以判断哪些问题，哪些问题还不能判断？
2. 本期操作是否符合自己事前的计划和规则？
3. 当前仓位、移动止损和减仓进度是否越界或需要处理？
4. 申请之后是否真实确认，处理后是否恢复到规则范围？
5. 经过多个周期，结果是否支持保留或修改下一版规则？

产品扩展的是人的记忆、计算、比较、追踪和复盘能力，不是鼓励增加金融杠杆。它可以帮助用户提高过程一致性和从错误中学习的能力，但不能保证持续赚钱。

### 产品主对象：用户声明的投资范围

一笔基金购买、单只基金和完整投资组合不是同一个对象。产品以**用户声明的投资范围**作为计算和评价边界：

- 默认可选择当前基金账户作为范围；
- 用户可以下钻到单只基金查看规则和操作；
- 仓位百分比的分母必须来自该范围内可靠的总资产或可投资资金；
- 若用户只提供单只基金金额而没有分母，系统可以复盘该基金的操作和止损，但不能声称其组合仓位合理；
- 产品不强迫用户先建立覆盖所有家庭资产的机构级总账，也不能把未声明的账户自动视为不存在。

这使“我买的这只基金怎样了”和“这只基金在我的投资范围中是否过重”成为两个可分别回答的问题。

## 2. 一次复盘怎样产生价值

产品按人的任务顺序工作，而不是按 Position、CashFlow、Benchmark 等数据库对象排列：

```text
声明投资范围与生效规则
  → 同步本期新增持仓、净值、申请和确认事实
  → 分别检查每个问题的证据是否够用
  → 对照计划检查操作
  → 检查仓位、移动止损和减仓恢复
  → 由用户处理或确认 unknown
  → 用真实确认和新快照复核是否恢复
  → 测量本期结果并分开评价过程与结果
  → 用多周期证据决定是否创建下一版规则草案
```

### 第一步：明确“按什么检查”

用户选择投资范围，并确认当时生效的个人规则，例如：

- 某只基金或某类基金的仓位上限/目标区间；
- 定投计划、单次计划金额或暂停新增条件；
- 哪些基金适用移动止损，以及回撤阈值；
- 触发后希望减仓到哪个区间。

系统可以帮助记录和计算，但没有用户事前规则时，不能事后发明“合理仓位”“应该减仓多少”或“这次操作异常”。此时只能显示事实、历史金额偏离等待确认信号。

真实账户第一次进入系统时先建立**管理基线**：已有交易保留为历史背景，不因为 Ledger 中没有当时的计划记录就被追溯判成“计划外”。用户保存第一条不可变事前计划后，计划核对从来源时间精度允许的下一日开始；只有此后发生、执行状态明确的操作，才允许判断是否存在计划记录或执行偏离。历史基线不能回填成事前计划。

### 第二步：先显示当前管理状态和唯一下一步

复盘首页先回答“管理闭环处于哪一步”，再按以下三组呈现具体事项，而不是先展示指标大全：

1. **需要你处理**：已有足够证据证明计划记录缺口、执行偏离、仓位越界、止损触发或减仓未完成；
2. **等待证据或执行**：说明是哪个对象、当前知道什么、缺什么、还能回答什么以及如何补救；
3. **已按计划管理**：只对证据覆盖的具体规则声明符合，不能用一个绿色“系统正常”代替全部检查。

每组按相同问题和恢复路径聚合，但组内必须保留基金、日期、方向和执行阶段。首层直接说明结论意味着什么、不能证明什么和下一步；内部状态与完整 Coverage 放在下钻层。管理状态不生成综合健康分，不评价基金优劣或未来收益。

用户首先获得的是可行动的偏离和依据，不是更多原始数据。

### 第三步：对照计划与真实执行

操作复盘至少区分：

- 本期无操作；
- 有事前计划且申请、确认与计划一致；
- 计划核对启用后，已确认但没有可验证事前记录的操作（这是管理流程缺口，不等于投资错误）；
- 已有合法事前记录但尚未由用户显式关联的操作；
- 对象、方向、金额/份额或时间窗口偏离计划；
- 暂停新增期间仍买入；
- 重复申请、待确认、部分确认、失败或撤销。

当前系统按历史金额分布识别“大额主动买入”只能作为**补充信号**。金额异常不必然违反计划，金额正常也可能是计划外操作；真正的纪律异常必须能回到当时有效的计划、规则和执行事实。

### 第四步：分别检查三类风险纪律

**仓位**

使用所选投资范围的可靠分母、当前持仓和用户上下限计算。分母未知时只把仓位判断降级为 unknown，不阻断操作对照或止损判断。

**移动止损**

使用适用基金、当时规则版本、合格净值、高水位和回撤阈值：创新高时止损线按规则上移；未创新高时不动；止损线不得下移。净值过期、缺失或分红/复权语义不清时保留 unknown，不制造触发结论。基金的移动止损表示进入复核或赎回计划，不等同于交易所实时止损单。

**减仓与恢复**

系统只按用户事前目标区间计算恢复范围所需的计划量，不预测最佳卖点。它继续跟踪计划量、申请量、部分/最终确认量、费用影响和操作后仓位。Action 被关闭或赎回已提交都不等于减仓完成；只有真实确认并重新计算已回到规则范围，才能标记恢复。

### 第五步：再评价结果与学习

纪律闭环稳定后，产品再回答本期赚亏、资金体验、风险和相对表现。过程和结果必须分开：

- 正收益但违反规则 = **过程违反 + 正结果**；
- 负收益但遵守规则 = **过程合规 + 负结果**。

单次结果不能证明规则有效或无效。只有跨周期的可比较证据才支持用户保留当前规则，或创建下一版本草案；历史版本和当时判断不得被覆盖。

## 3. 专业概念如何按问题进入

本轮不是删除 A 股基金里的专业概念，而是让每个概念对具体用户判断负责。

| 概念类别 | 何时需要 | 不需要时怎样处理 |
| --- | --- | --- |
| 投资范围、基金身份、持仓/份额、申请与确认、净值日期、生效规则版本、计划与实际 | P0 纪律与执行闭环的共同事实 | 缺失时只降级受影响的判断，并说明缺口 |
| 总资产/可投资资金、Cash、仓位上下限 | 判断基金在用户投资范围中的仓位 | 不做仓位百分比结论；Cash 不作为所有复盘的强制入口 |
| 高水位、移动止损阈值、分红/复权语义 | 判断止损线是否上移或触发 | 不显示伪造止损线；陈旧或不清楚时为 unknown |
| 触发原因、目标区间、计划/申请/确认量、操作后快照 | 判断减仓多少、进行到哪、是否恢复 | 不把 Action 关闭或申请提交当作完成 |
| 复盘期间、估值边界、费用、外部资金流 | P1 计算 Absolute Return、TWR、MWR/XIRR | 不阻断可独立完成的 P0 纪律判断 |
| Target | 判断是否达到用户自己的目标 | 不等同于 Benchmark |
| Benchmark、return type、可比期间 | 判断相对表现和 Excess Return | 缺失只阻断相对表现，不阻断纪律复盘或绝对结果 |
| 币种、FX | 所选范围跨币种或进行跨币种比较 | 初始人民币 A 股基金范围不作为 P0 前置清单 |
| 税、赎回费用 | 相应账户确有税务问题，或费用影响减仓确认/绩效 | 按受影响判断启用，不笼统要求所有用户填写 |
| Attribution 和行为统计 | P2 且数据粒度、样本量满足 | 不编造收益来源，不作心理诊断 |

工程内部可继续使用 `VALID | PARTIAL | STALE | INSUFFICIENT_DATA | FAILED | UNKNOWN`，但页面必须翻译成“哪个问题、当前结论、缺什么、还能回答什么”。不能用一个全局 `INSUFFICIENT_DATA` 把所有独立问题一起阻断。

| 操作异常 | 已实现 | DecisionRecord/OperationPlan、ExecutionLink、计划合规与历史金额补充信号 | 来源时间精度不足或关联不确定时保持 unknown/unlinked |

## 5. 当前交付：P0 纪律与执行复盘

### 阶段出口

基于用户声明的投资范围、事前规则和可信事实，不依赖 AI 地回答：

- 本期操作是否有计划，实际执行与计划是否一致；
- 仓位是否越过用户边界；
- 移动止损线是否应上移、是否触发；
- 减仓处于计划、申请、部分确认、确认未恢复还是已恢复；
- 每个问题证据是否足够，为什么，以及下一步由人处理什么。

### 本次包含

- InvestmentScope 和规则适用范围的产品/工程契约；
- 版本化计划与操作事实的对照；
- 申请、部分确认、确认、失败、撤销和操作后复核语义；
- 仓位判断、移动止损状态、减仓计划与恢复进度；
- 每个判断独立的 Coverage、unknown 原因和证据下钻；
- `/investment/review` 的 P0 产品切片与可运行三栏闭环；
- 目标真实环境中的实际操作证据与可核实来源锚点。

### 本次不把哪些能力塞进 P0

- 完整 Absolute/TWR/MWR/XIRR、专业风险测量和 Benchmark 比较属于 P1；
- Attribution、决策评价深化和行为统计属于 P2；
- StrategyHypothesis 跨周期状态属于 P3；
- AI Review 属于 P4。

这些能力没有被删除。P1 的 Measurement 仍是 P2 Attribution 与 Appraisal 的有效性前提；只是它们不再阻断能独立解决用户首要痛点的 P0 纪律闭环。

## 6. 当前工作包

工作包按用户结果组织，不按 Agent 角色拆分。实现、排错和非私人验证默认由当前交付者纵向完成；只有某个关键来源语义必须进入私人真实环境才能证明时，才按[最小授权验证](../standards/main-agent-authorized-validation.md)补足脱敏证据。

| 工作包 | 用户结果 | 产品责任 | 人的决定与验收 |
| --- | --- | --- | --- |
| WP0-1 投资范围、规则与数据状态 | 知道系统检查什么、按哪版规则，以及每个问题能否判断 | InvestmentScope、版本规则、按问题 Coverage、JudgmentResult 和不丢历史的 migration | 定义投资范围、规则语义和可接受的 unknown；总资产未知时，其他可判断问题仍应工作 |
| WP0-2 计划与真实执行 | 区分无操作、计划内、计划外/超量，以及待确认、部分确认、失败和撤销 | 不可覆盖的事前记录、execution lifecycle、偏离维度和可核实来源锚点 | 确认异常理由符合自己的规则；申请与确认不明时不得自动猜测 |
| WP0-3 仓位、止损与减仓恢复 | 知道仓位是否越界、止损线为何变化、减仓进度及是否恢复 | 可复算判断、分母 gate、止损线单调不降、陈旧数据降级和操作后复算 | 事前声明阈值与目标；触发只生成待处理事项，不执行交易 |
| WP0-4 一页复盘 | 从“需处理 → 已符合 → 暂不能判断”完成检查并下钻到事实 | `/investment/review` 统一查询与页面，UI 不重算 Core、不用“系统正常”覆盖未检查项 | 在真实 Chrome 完成用户路径，判断产品是否降低完整复盘成本 |

真实来源能力只决定输入资格，不成为业务规则 Oracle；任何阶段都不通过真实账户值交接。范围、日期、状态或来源语义只能靠猜，需要扩大授权或迁移会丢记录时，保持 unknown 或停止。

## 7. 怎样证明它对人友好

### 10 分钟人工审查脚本

只使用人工构造的数据，不使用真实账户值：

1. **1 分钟：范围与规则**——指出系统正在检查什么范围、哪一版规则，单只基金与组合仓位有什么区别。
2. **2 分钟：操作对照**——分别解释无操作、计划内、无计划、超计划和暂停期新增；指出历史金额异常为何只是信号。
3. **2 分钟：仓位与独立 unknown**——识别仓位越界；移除总资产分母后，确认只有仓位判断降级，其他可回答问题仍保留。
4. **2 分钟：移动止损**——验证创新高时上移、未创新高时不动、陈旧净值时 unknown，且止损线永不下移。
5. **2 分钟：减仓恢复**——依次识别已计划、已申请、部分确认、已确认但仍越界和确认后恢复。
6. **1 分钟：边界**——说明系统没有替用户决定阈值、没有自动交易，也不能保证未来盈利。

### UX Gate

以下任一项失败，P0 不得标记完成：

- 首屏按金融对象、Agent 或指标组织，而不是按用户问题组织；
- 用户必须先补齐 Benchmark、现金流、FX 或税才能检查可独立回答的纪律问题；
- 一个缺失项把所有判断都变成 `INSUFFICIENT_DATA`；
- “正常”没有列明已检查的规则和未覆盖问题；
- 计划、申请、部分确认、确认、Action 关闭和恢复被混为一谈；
- 历史金额偏离被直接定义为操作异常；
- 止损线下移，或陈旧 NAV 仍推进状态；
- 用户看见偏离却不知道原因、证据和下一步；
- 页面诱导自动买卖、“盈利即正确”或“亏损即错误”；
- 关键数值比对（仓位 vs 区间、回撤 vs 峰值、构成 vs 合计）没有视觉编码，靠心算；
- 证据页的聚合数不能下钻到构成明细逐笔核对。

人工审查记录场景、用户答案、耗时、误解点、是否需要外部计算和 Required change。通过脚本只证明任务可理解，不证明长期决策质量已改善。

## 9. 完成标准与核心反例

每个当前工作包都必须同时满足：

1. 输入、版本、Coverage、输出和失败状态有明确契约；
2. Core 只消费真实来源标准化事实，不依赖 LLM；其正确性须由目标真实环境的最终页面结果验收；
3. expected 来自手算、独立公式、性质/不变量或状态转换；
4. `normal/empty/partial/stale/failed/unknown` 有按问题可见的行为；
5. migration、reload、幂等和历史版本不丢失；
6. UI 能从结论下钻到事实、规则版本、Coverage、限制和下一步；
7. tests、typecheck 和 production build 结果如实记录；
8. 不引入真实基金名、金额、收益、Cookie、Token、Raw Snapshot、登录态或完整 Network Logs；
9. 通过对应人的验收问题和 10 分钟脚本；
10. 实现与匹配证据完成后才升级本文状态。

P0 至少覆盖这些人工反例：

- 规则内且本期无操作，只对已覆盖判断显示无需处理；
- 有计划且已确认；无计划、超计划和暂停期间新增；
- 仓位超限，以及分母缺失时只有仓位 unknown；
- NAV 创新高、未创新高、陈旧和分红/复权语义不清；
- 减仓已计划、已提交、部分确认、确认后仍未恢复和已恢复；
- 交易历史 partial 时只降级依赖完整历史的判断；
- 正收益但过程违规、负收益但过程合规；
- Benchmark 缺失不阻断 P0；跨币种/税务不适用时不进入前置清单。

详细对象、不变量和真实环境验收边界在[工程附录](reference/investment-review-engineering.md)中；它不是理解本次需求的前置材料。

## 10. 不可违反的边界

1. 用户的 InvestmentScope 和事前规则先于评价；没有规则时不发明合理仓位、止损或减仓。
2. 每个用户判断拥有自己的最小证据和状态；缺失不能无理由扩散为全局失败。
3. Decision 与 Execution 分开；计划、申请、部分确认、确认、失败、撤销和前后快照不能合并为 Action status。
4. 历史使用当时有效的 Policy、Rule、Decision、Benchmark 和 Profile 版本；当前编辑不回写历史。
5. 止损线只上移或不动；陈旧、partial 或 unknown NAV 不推进状态。
6. 减仓触发只生成待人处理事项；真实确认和操作后恢复必须分别验证。
7. Decision Quality 与 Outcome Quality 分离；收益不参与 P0 过程合规状态计算。
8. Target 与 Benchmark 分开；Benchmark 事前确定并版本化，不事后重选。
9. P1 的 TWR 与 MWR/XIRR 回答不同问题；现金、费用和外部现金流不能静默消失，不足一年不伪装成年化实绩。
10. Attribution 必须匹配数据能力；证据不足显示 residual/limitation，不制造 allocation、selection 或心理原因。
11. 行为 Finding 需要样本、阈值、反例和替代解释，不构成心理诊断。
12. AI 不计算核心指标、不预测市场、不改变规则或状态；重要陈述必须引用确定性证据。
13. 实现、排错和非私人验证纵向完成，不因复杂度拆成平行 Agent 流程；完成结论必须来自与主张匹配的真实环境。
14. 私人来源只按[最小授权验证](../standards/main-agent-authorized-validation.md)确认能力与缺口；不设计规则、不评价仓位、不执行账户操作，也不输出或保存任何可识别个人的原始内容。
15. 真实登录环境是验收目标时，隔离 profile 不能替代用户实际 Chrome；结论必须使用带环境的状态。
16. 系统不自动买入、卖出、申购、赎回、调仓、转账或交易。

- **采集（2026-08-23 改名，原“数据”）**：采集/健康/覆盖/缺口/清除；**牛熊模拟器迁入复盘**。“从采集 JSON 导入”卡双入口（2026-08-23）：①内置正式脱敏快照（由 Vite 生成资源 URL）；②本地 JSON 文件导入（插件导出的完整备份或脱敏快照，协议 eastmoney-source-capture/1.0，同一 toInvestmentDataset → SyncService → scope:real-account 链路）——换浏览器/换电脑无需重新采集；错误路径显式提示（非法 JSON / 协议不匹配），同一文件可重复选择。插件待导入、内置快照、本地 JSON 三条导入路径统一显示当前采用的数据来源；导入期间不混入上次采集分支和历史统计，成功后整块状态提示消失；选择快照或文件即代表放弃同一时刻未采用的插件暂存批次，成功写账后将其标记为 discarded 并清场，避免旧批次继续阻塞重新采集。插件 popup（v3.1.1）同步加「下载脱敏快照」：复用 desensitizeSource 和残留自检（32 位交易/追踪 ID 与银行卡尾号零残留，宁可失败不生成假脱敏文件），文件名与仓库正式快照一致（eastmoney-source-desensitized.json），采集逻辑变更后可直接替换 `project-support/data-snapshots/investment/` 同名唯一源文件；导出直接进入浏览器默认下载目录，避免“另存为”窗口关闭 popup 后使异步响应端口提前断开。

### 12.3 默认规则集与第 10 节边界的调整

为降低"逐条声明阈值"的管理成本（用户反馈规则页 21 条逐条编辑太重），规则页改为**默认规则集优先**：`engines/policy/default-rules.ts` 提供基于 `rule-rationale.ts` 风控惯例的示例阈值（仓位 0–25% 目标 15%、移动止损 10%、目标止盈 20%、减仓目标 10–20%），用户一键采纳即生效，无需逐条填写；对某条有疑问可"疑问→深度分析"跳行动页生成 Context Package 交通用模型，据结论在自定义区调整或忽略。

这是对第 10 节"没有规则时不发明合理仓位"的**边界调整**（非违反）：默认值定位为"理论原则的量化惯例参考、非权威值、可外包分析后调整/忽略"，仍不声称是"合理仓位"或大师策略权威阈值；用户可随时自定义或重置。理论提供原则、默认值提供起点、外包分析提供深度判断、用户做最终接受/忽略——管理成本与边界诚实性兼顾。

### 12.4 历史周期场景压力测试（机构 scenario analysis 思路）

把当前真实采集持仓**平移到真实历史市场周期净值曲线**上做压力测试——A股对 A 股历史（2015 杠杆牛熊/2018 单边熊/2021 核心资产顶）、美股对美股（2008 金融危机/2022 加息熊）、黄金对 2020 避险牛——看该历史风格下组合的回撤、末态暴露与配置偏离。复盘页加"历史周期场景压力测试"卡（虚构模拟器与配置对比并存）。

- `engines/scenario/historical-cycles.ts`：9 段示意性周期（A股 3 + 美股 2 + 黄金 1 + 港股 3），月度涨幅为基于公开历史的近似值，每段带 disclaimer。
- `engines/scenario/stress-test.ts`：`buildHistoricalStressTest` 以当前市值为基准平移（不模拟交易），重算回撤与末态暴露/偏离；未匹配周期基准的持仓（如 A 股资产在美股周期下）市值不变、标注 matched=false，不伪造收益。复用 `aggregateExposure`/`buildAllocationDrift`。
- 边界：示意性历史风格，**非精确回测**；平移非预测；不触碰真实账户（纯本地内存计算）。与第 10 节边界一致。
- 该卡片必须在实际部署页面用真实持仓操作，核对匹配/未匹配持仓、回撤、末态 drift、免责声明和失败状态；示意周期计算或构建成功不能替代验收。
- 验收必须在真实持仓页面执行周期选择与结果核对；静态计算或脱离真实数据的测试脚本不能替代该路径。
- **一键操作反馈**：历史周期加 `buildAllCyclesStressTest` 一次跑完 9 段返回“最脆弱/最稳健场景”汇总（各周期回撤+末态偏离+最差资产）；牛熊演练加“一键跑完整周期”自动推进到末态。把“手动选周期/逐轮推进 + 逐层下钻”转为“一键运行 + 直接返回结论反馈”，降低操作与审查成本。
- **演练模式与压力测试/各页联动（2026-08-23）**：牛熊演练是“接管式”实现（启动时 clearImportedFacts 清空真实导入数据、全局切模拟态，让复盘机械检查/待办围绕演练运转——这是演练的产品价值），因此演练期间凡消费“当前持仓”的功能都受影响。本轮修复：①原实现把压力测试按 isSimulator 一刀切暂停，与演练卡自身提示“末态回撤可在上方压力测试复算”自相矛盾（演练结束后持仓恢复真实、末态消失根本无法复算）——改为演练中**不暂停**，输入自动为演练持仓，卡内 info 提示标注“当前按演练第 N 期持仓计算，正好复算演练末态；真实持仓测试结束后进行”；②持仓页保持暂停（它自称真实持仓，模拟冒充会误导）但文案讲清因果与去向（演练持仓去复盘页看）；③总览/明细页补演练 info 标注（指标曲线为模拟值/交易不用于对账），消除“模拟数据冒充真实”的误导缺口；④演练 intro 补预期管理（演练期间哪些页受影响、结束一键恢复）。

**明细核对（证据页，零新依赖，只读翻译不加标记）**：

- 对账锚点条：首末交易日期、总笔数/基金数、按月笔数双色堆叠柱（红=买入笔数、绿=卖出笔数，买/卖构成直接可见不依赖悬停；说明行带色块图例，无买卖交易但有其他类型的月份给灰色最小段防断档），悬停为 el-tooltip 当月明细（如「2025-08：共 165 笔（买 50 / 卖 115）」）+ 柱色加深反馈——拿着来源 App 按月对总数即可，不必逐页翻。
- 逐笔核对（二级折叠默认收起）：日期/基金/业务类型/**申请值+单位/确认值+独立单位**/状态/来源单号，支持基金+方向过滤与分页；失败/撤销交易也如实列出，不加任何标记（列集即采集字段，用户反馈明确不要系统概念列，「系统分类」behaviorType 列已删，其信号留在行动页）。基金列与下拉均为“六位数代码+名称”格式（下拉可输入过滤），代码是跨 App 核对的稳定锚点；筛选变化时页码回到第 1。业务类型/状态列显示来源原文（Transaction.businessTypeText/statusText 适配器透传，如「银行卡定投」「已受理(支付完成)」），系统翻译仅作 tag 色与聚合口径，不再覆盖原文，也不会因映射不上而生造「未知」。
- 已确认订单申请金额构成：摘要指标为**始终直接可见的卡片**（不做折叠——核心数字不应多要一次点击）；只纳入全额确认且申请单位为人民币的买入订单申请金额，部分确认、仅受理、失败和撤销订单均不计入，确认份额不得当金额。展开/收起、逐笔表、筛选和分页行为维持原契约。名称缺口修复：历史交易过但已无持仓详情的基金（assets 表缺失）由适配器从交易记录 productName 补“仅名称”骨架元数据（分类字段全 unknown 不伪造），避免下拉/表格显示纯代码。

- 交易来源语义：`captureMethod` 只描述插件采集、手动导入或模拟器生成；`executionMethod` 只描述来源能确认的银行卡定投等执行方式。旧 `sourceType` 仅兼容读取，不再把 `unknown` 改写成 `auto_collect`，也不再把采集路径当执行方式。
- 原始事实、标准化账本与深度分析分层：插件待导入批次必须在 ACK 清除前把完整 `eastmoney-source-capture/1.0` 对象写入本地 IndexedDB `sourceCaptures`；内置快照和本地 JSON 替换导入同样保留对应原档，替换标准化事实时不删除历史原档。原始档案是核查采集字段、发现适配损失的事实底稿；标准化账本是指标与规则判断的唯一计算输入；深度分析只是派生消费者，不得成为核心数据或反向覆盖前两层。GPT Context 只绑定当前导入记录 `capturedAt` 对应的原档，并附加与当前问题相关、去除账户/银行卡/认证/交易追踪标识的原字段核查附件；历史原档不得错配给当前账本，完整未删减对象不外传。旧账本若没有对应原档必须明确显示“当前数据无对应原档”，不能假装可追溯；重新采集或重新导入后补齐。
- 单偏离 Context 时点与覆盖语义：必须把“全账户采集任务/实际观测覆盖”与“本标的从全账户事实中筛出的关联观测”分开，后者的条数不能被描述为本标的历史完整性。`PolicyVersion` / `StrategyRuleVersion` 分别记录实际 `createdAt` 与 `effectiveFrom`；旧版本缺创建时点时不得用生效日反推。规则生效或创建晚于持仓快照时，只能表达“当前用现行规则检查最新已知状态”，不得倒推历史违规或评价生效前交易。基金 `currencies` 在上下文统一称“份额计价币种”，与账户 `baseCurrency` 分开。`InvestmentScope.effectiveFrom` 统一解释为“范围版本生效日”，不是行情或交易覆盖起始日，并同时展示首次纳入本地管理与账户分母快照日；分母快照日不是底层持仓净值日。原始核查附件补账户总资产和当前全部持仓的精简来源锚点。止盈/止损当前状态只在成本、高水位、止损线等必要口径存在时派生；缺失时必须明确未知，不能用来源展示收益率或当前净值替代。
- 单偏离 Context 估值与规则口径：账户/组合采集形成的快照日必须与每只基金的底层净值日分开；输出本标的净值滞后自然日、其他持仓净值日期范围及异步估值提示，接近阈值时不得把百分点偏离解释得过于精确。目标止盈固定使用“当前持仓成本收益率 =（当前持仓市值－可确认的当前持仓成本）/可确认的当前持仓成本”，成本缺失即 unknown。减仓目标区间表示“减仓后仓位减到多少”，计划量按降至目标上限计算，不得解释为卖出当前持仓的比例。原始 `account.assetTotal` 三项按数组位置附加标准化用途；来源没有字段名的第二项明确保持语义未知，不猜测为当日收益。
- Context 事实分层与派生契约：原始事实用于核查采集，标准化事实用于统一业务语义；不重算来源业务指标，但允许从标准化事实计算仓位差、日期差、持仓汇总等明确且可追溯的上下文派生量，并必须标记派生依据。只有持久化了原字段名时才可称“持仓 profitValue/profit”；旧账本未保留字段名时统一称 `HoldingSnapshot.pnl` 收益金额标准化槽位，不得直接提升为“浮盈亏”。其持仓聚合仍是可追溯派生量，但不能反向证明底层语义。无字段名的 `assetTotal[1]` 即使数值相同，也只能作为一致性核查，不能反向取得任何一方的业务语义。净值新鲜度同时给出相对快照的自然日差和相对账户最新 NAV 日期差，并说明自然日包含非交易日、不等同于交易日滞后。
- Context 关键指标来源标签：关键金额、比例、日期、规则和估算统一使用 `provenance/type`，枚举为 `source`（原始采集）、`normalized`（标准化账本）、`adapter-mapped`（适配器字段或位置映射）、`derived`（可追溯计算）和 `declared-rule`（用户声明规则），并在同一标签内写明依据。标签必须覆盖账户总资产、持仓市值、profitValue、累计盈亏、仓位、现金残差、净值/净值日、目标区间、当前派生状态、交易汇总和减仓估算；不能只在附件或段落说明一次。
- Context 分母、现金与累计盈亏语义：`PortfolioSnapshot.cash` 是“账户总资产－当前持仓市值合计”的非负残差派生值，不是来源直接披露的现金；残差为 0 只表示当前快照在容差内没有正残差。`cumulativePnl` 优先绑定来源具名 `totalProfit`；当前来源只有 `assetTotal[2]` 时，必须说明依据是适配器的账户摘要位置契约、原采集未保留字段标签，属于位置映射证据且不能由当前持仓盈亏反推。
- 减仓计划分母契约：减仓后仓位目标不唯一决定卖出量。赎回款留在投资范围并计入现金时，估算 `x=M−tD`；赎回款转到银行卡并离开范围、分母与持仓同步减少时，估算 `x=(M−tD)/(1−t)`。创建计划前必须由人确认资金去向，不得从历史交易方式猜测。计划金额/份额统一标记为基于当前快照的估算值，不计净值变化、费用与确认时差；真实成交后必须读取新持仓和新账户分母，重新检测是否回到目标区间。
- 数据覆盖语义：最近同步状态与实际观测覆盖分开显示。同步完成量说明接口/分页任务是否跑完；实际观测单独列记录数、最早/最晚日期与不连续边界，禁止把“完成”解释成区间内逐日齐全。
- 持仓收益率语义：天天基金 `profitPercent` 作为来源展示值保存，页面和 GPT 上下文同时标注来源字段及“来源未披露公式”；只有本地真实计算时才允许声明计算公式。
- 状态/类型映射修复：「已撤单」不含「撤销」二字导致 23 笔撤单被标 status=unknown（显示“状态未知”）且撤单买入被计入买入金额，正则补「撤单」后归 cancelled 并从合计排除；TRANSFER 之前无中文标签（裸英文）且不在方向筛选项，补「转入/转出」；映射前统一压缩来源文本空白，防排版空格漏匹配。
- 每日盈亏核对：范围/点数/资产数 + 连续缺口 >3 天区间 warning（只陈述“这些日期无记录”，不断言漏采）。

**边界不变**：不发明阈值、缺口断线不插值、未匹配周期不画曲线、明细表不加异常标记、UI 不重算 Core。echarts 经 `echarts-vendor` 独立分包（gzip ≈214KB），只随投资路由懒加载，不进首屏。图表共用层 `useChart` 以 `replaceMerge:["series"]` + series 稳定 id 做差分更新，避免整图重建重播入场动画导致的回放闪烁。

**验收边界**：本项目不维护脱离真实投资页面和真实采集来源的 Vitest 完成门禁。类型检查、构建和静态计算只能用于排错；完成结论必须来自 Chrome DevTools MCP 接管用户实际 Chrome 后，对真实页面、存储、来源附件、刷新与失败恢复路径的核验。

**外部深度分析事实包**：上下文只负责输出带来源分层的历史快照、用户已声明规则、实际观测记录、明确派生值和数据缺口，不内置“支持/反对”“市场风格归因”等分析提纲，也不把规则理论说明当成分析结论。外部模型必须自行补充并注明生成时点之后的市场行情、基金公告、宏观环境与同类比较来源；缺失事实保持 unknown。标准化账本没有持久化字段级来源路径时，只能标为 `normalized` 并要求回查原始附件或重新采集，不能固定宣称来自某个原字段。

### 12.6 本地账本操作追溯（2026-08-30）

Investment Ledger v4 新增追加式关键操作链，用于追溯数据导入、事实清除、完全清空、纪律版本、事前计划、执行关联和减仓计划。事件只保存用户可理解的摘要、类型、计数和业务主键，不复制账户、持仓、交易或原始采集正文；详情按逐事件字段白名单收敛，并以 SHA-256 绑定上一条事件。

关键规则、计划、执行关联、清除和导入完成记录与对应审计事件在同一 IndexedDB 事务提交；同页面多 Ledger 实例共享写队列，支持 Web Locks 的浏览器还会跨标签页串行化链尾分配。审计详情采用逐事件字段白名单，不再依赖敏感字段名黑名单。模拟器推进和回退不写入真实操作链，自动维护与人的主动操作分别标记。

“明细”页直接显示链内一致性、最近关键操作和短哈希锚点，并明确证明边界：它可以发现链内记录被修改、插入或删除，但没有外部可信锚点时不能独立证明整链未被重写或尾部未被截断。完全清空尊重本地数据删除边界，会删除旧链并以新的 `ledger.reset` 事件建立新链。

该能力采用 Apache Maka 的“规范事件事实流与投影分离”原则，但没有引入 Maka 完整运行时或源文件依赖；候选比较、固定提交和商业判断见 [`research/github-trending-commercial-assessment-20260830.md`](research/github-trending-commercial-assessment-20260830.md)。
