## 1. 这是什么产品

Investment Review 是个人 A 股公募基金的**纪律与学习工具**，不是机构绩效系统的缩小版，也不是收益看板或 AI 买卖建议。

它首先帮助用户回答五个反复出现的问题：

1. 数据足以判断哪些问题，哪些问题还不能判断？
2. 本期操作是否符合自己事前的计划和规则？
3. 当前仓位、移动止损和减仓进度是否越界或需要处理？
4. 申请之后是否真实确认，处理后是否恢复到规则范围？
5. 经过多个周期，结果是否支持保留或修改下一版规则？

产品扩展的是人的记忆、计算、比较、追踪和复盘能力，不是鼓励增加金融杠杆。它可以帮助用户提高过程一致性和从错误中学习的能力，但不能保证持续赚钱。

### 产品主对象：用户声明的投资范围

一笔基金购买、单只基金和完整投资组合不是同一个对象。产品以**用户声明的投资范围**作为计算和评价边界：

- 默认可选择当前基金账户作为范围；
- 用户可以下钻到单只基金查看规则和操作；
- 仓位百分比的分母必须来自该范围内可靠的总资产或可投资资金；
- 若用户只提供单只基金金额而没有分母，系统可以复盘该基金的操作和止损，但不能声称其组合仓位合理；
- 产品不强迫用户先建立覆盖所有家庭资产的机构级总账，也不能把未声明的账户自动视为不存在。

这使“我买的这只基金怎样了”和“这只基金在我的投资范围中是否过重”成为两个可分别回答的问题。

## 2. 一次复盘怎样产生价值

产品按人的任务顺序工作，而不是按 Position、CashFlow、Benchmark 等数据库对象排列：

```text
声明投资范围与生效规则
  → 同步本期新增持仓、净值、申请和确认事实
  → 分别检查每个问题的证据是否够用
  → 对照计划检查操作
  → 检查仓位、移动止损和减仓恢复
  → 由用户处理或确认 unknown
  → 用真实确认和新快照复核是否恢复
  → 测量本期结果并分开评价过程与结果
  → 用多周期证据决定是否创建下一版规则草案
```

### 第一步：明确“按什么检查”

用户选择投资范围，并确认当时生效的个人规则，例如：

- 某只基金或某类基金的仓位上限/目标区间；
- 定投计划、单次计划金额或暂停新增条件；
- 哪些基金适用移动止损，以及回撤阈值；
- 触发后希望减仓到哪个区间。

系统可以帮助记录和计算，但没有用户事前规则时，不能事后发明“合理仓位”“应该减仓多少”或“这次操作异常”。此时只能显示事实、历史金额偏离等待确认信号。

真实账户第一次进入系统时先建立**管理基线**：已有交易保留为历史背景，不因为 Ledger 中没有当时的计划记录就被追溯判成“计划外”。用户保存第一条不可变事前计划后，计划核对从来源时间精度允许的下一日开始；只有此后发生、执行状态明确的操作，才允许判断是否存在计划记录或执行偏离。历史基线不能回填成事前计划。

### 第二步：先显示当前管理状态和唯一下一步

复盘首页先回答“管理闭环处于哪一步”，再按以下三组呈现具体事项，而不是先展示指标大全：

1. **需要你处理**：已有足够证据证明计划记录缺口、执行偏离、仓位越界、止损触发或减仓未完成；
2. **等待证据或执行**：说明是哪个对象、当前知道什么、缺什么、还能回答什么以及如何补救；
3. **已按计划管理**：只对证据覆盖的具体规则声明符合，不能用一个绿色“系统正常”代替全部检查。

每组按相同问题和恢复路径聚合，但组内必须保留基金、日期、方向和执行阶段。首层直接说明结论意味着什么、不能证明什么和下一步；内部状态与完整 Coverage 放在下钻层。管理状态不生成综合健康分，不评价基金优劣或未来收益。

用户首先获得的是可行动的偏离和依据，不是更多原始数据。

### 第三步：对照计划与真实执行

操作复盘至少区分：

- 本期无操作；
- 有事前计划且申请、确认与计划一致；
- 计划核对启用后，已确认但没有可验证事前记录的操作（这是管理流程缺口，不等于投资错误）；
- 已有合法事前记录但尚未由用户显式关联的操作；
- 对象、方向、金额/份额或时间窗口偏离计划；
- 暂停新增期间仍买入；
- 重复申请、待确认、部分确认、失败或撤销。

当前系统按历史金额分布识别“大额主动买入”只能作为**补充信号**。金额异常不必然违反计划，金额正常也可能是计划外操作；真正的纪律异常必须能回到当时有效的计划、规则和执行事实。

### 第四步：分别检查三类风险纪律

**仓位**

使用所选投资范围的可靠分母、当前持仓和用户上下限计算。分母未知时只把仓位判断降级为 unknown，不阻断操作对照或止损判断。

**移动止损**

使用适用基金、当时规则版本、合格净值、高水位和回撤阈值：创新高时止损线按规则上移；未创新高时不动；止损线不得下移。净值过期、缺失或分红/复权语义不清时保留 unknown，不制造触发结论。基金的移动止损表示进入复核或赎回计划，不等同于交易所实时止损单。

**减仓与恢复**

系统只按用户事前目标区间计算恢复范围所需的计划量，不预测最佳卖点。它继续跟踪计划量、申请量、部分/最终确认量、费用影响和操作后仓位。Action 被关闭或赎回已提交都不等于减仓完成；只有真实确认并重新计算已回到规则范围，才能标记恢复。

### 第五步：再评价结果与学习

纪律闭环稳定后，产品再回答本期赚亏、资金体验、风险和相对表现。过程和结果必须分开：

- 正收益但违反规则 = **过程违反 + 正结果**；
- 负收益但遵守规则 = **过程合规 + 负结果**。

单次结果不能证明规则有效或无效。只有跨周期的可比较证据才支持用户保留当前规则，或创建下一版本草案；历史版本和当时判断不得被覆盖。

## 3. 专业概念如何按问题进入

本轮不是删除 A 股基金里的专业概念，而是让每个概念对具体用户判断负责。

| 概念类别 | 何时需要 | 不需要时怎样处理 |
| --- | --- | --- |
| 投资范围、基金身份、持仓/份额、申请与确认、净值日期、生效规则版本、计划与实际 | P0 纪律与执行闭环的共同事实 | 缺失时只降级受影响的判断，并说明缺口 |
| 总资产/可投资资金、Cash、仓位上下限 | 判断基金在用户投资范围中的仓位 | 不做仓位百分比结论；Cash 不作为所有复盘的强制入口 |
| 高水位、移动止损阈值、分红/复权语义 | 判断止损线是否上移或触发 | 不显示伪造止损线；陈旧或不清楚时为 unknown |
| 触发原因、目标区间、计划/申请/确认量、操作后快照 | 判断减仓多少、进行到哪、是否恢复 | 不把 Action 关闭或申请提交当作完成 |
| 复盘期间、估值边界、费用、外部资金流 | P1 计算 Absolute Return、TWR、MWR/XIRR | 不阻断可独立完成的 P0 纪律判断 |
| Target | 判断是否达到用户自己的目标 | 不等同于 Benchmark |
| Benchmark、return type、可比期间 | 判断相对表现和 Excess Return | 缺失只阻断相对表现，不阻断纪律复盘或绝对结果 |
| 币种、FX | 所选范围跨币种或进行跨币种比较 | 初始人民币 A 股基金范围不作为 P0 前置清单 |
| 税、赎回费用 | 相应账户确有税务问题，或费用影响减仓确认/绩效 | 按受影响判断启用，不笼统要求所有用户填写 |
| Attribution 和行为统计 | P2 且数据粒度、样本量满足 | 不编造收益来源，不作心理诊断 |

工程内部可继续使用 `VALID | PARTIAL | STALE | INSUFFICIENT_DATA | FAILED | UNKNOWN`，但页面必须翻译成“哪个问题、当前结论、缺什么、还能回答什么”。不能用一个全局 `INSUFFICIENT_DATA` 把所有独立问题一起阻断。

P0 已形成可运行闭环，但“运行时存在”不等于外部来源已经覆盖所有业务语义。

| 投资范围与仓位 | 已实现 | InvestmentScope、分母 gate、单基金/组合仓位判断、规则版本引用 | 分母缺失时按问题 unknown，不声称仓位合理 |
| 个人规则 | 已实现 | StrategyRuleVersion、仓位区间、定投/暂停、移动止损、减仓目标 | 阈值必须由用户事前声明，系统不替用户发明 |
| 操作异常 | 已实现 | DecisionRecord/OperationPlan、ExecutionLink、计划合规与历史金额补充信号 | 来源时间精度不足或关联不确定时保持 unknown/unlinked |

| 一页任务复盘 | 已实现 | canonical `/investment/review`、管理状态、三栏结论、原因/限制/下一步与路由恢复路径 | 页面应直接按真实用户任务持续验证，不增加验收专页 |
| 绩效测量与过程/结果分离 | 未实现 | DailyPnL 等局部事实 | 缺 Absolute/TWR/MWR、专业回撤、Benchmark gate、Decision Appraisal |

当前 P0 运行时已经降低规则对照、状态计算、待办追踪和恢复确认成本；P1–P4 仍未进入运行时。真实来源缺少用户规则或未提供完整 execution lifecycle 时，页面只展示已知事实和对应 unknown，不制造具体规则判断。

## 5. 当前交付：P0 纪律与执行复盘

### 阶段出口

基于用户声明的投资范围、事前规则和可信事实，不依赖 AI 地回答：

- 本期操作是否有计划，实际执行与计划是否一致；
- 仓位是否越过用户边界；
- 移动止损线是否应上移、是否触发；
- 减仓处于计划、申请、部分确认、确认未恢复还是已恢复；
- 每个问题证据是否足够，为什么，以及下一步由人处理什么。

### 本次包含

- InvestmentScope 和规则适用范围的产品/工程契约；
- 版本化计划与操作事实的对照；
- 申请、部分确认、确认、失败、撤销和操作后复核语义；
- 仓位判断、移动止损状态、减仓计划与恢复进度；
- 每个判断独立的 Coverage、unknown 原因和证据下钻；
- `/investment/review` 的 P0 产品切片与可运行三栏闭环；
- 目标真实环境中的实际操作证据与可核实来源锚点。

### 本次不把哪些能力塞进 P0

- 完整 Absolute/TWR/MWR/XIRR、专业风险测量和 Benchmark 比较属于 P1；
- Attribution、决策评价深化和行为统计属于 P2；
- StrategyHypothesis 跨周期状态属于 P3；
- AI Review 属于 P4。

这些能力没有被删除。P1 的 Measurement 仍是 P2 Attribution 与 Appraisal 的有效性前提；只是它们不再阻断能独立解决用户首要痛点的 P0 纪律闭环。

## 6. 当前工作包与 A/B 分工

这里采用[主力 Agent—授权验证 Agent—人类裁决者协作标准](../standards/main-agent-authorized-validation.md)的非对称分工：

- **Agent A = 主力交付 Agent**：拥有每个工作包的纵向结果，完成需求细化、产品/工程契约、Core、迁移、UI、静态排错和修复，常态承担 80% 以上工作；
- **Agent B = 授权真实来源验证 Agent**：不是通用 reviewer。只有 A 已完成上述工作，且一个关键主张仍只能由天天基金真实登录环境或私人来源事实证明时，才由维护者授权 B 做一次窄范围、只读、脱敏验证；
- **维护者 = 授权者与裁决者**：定义 InvestmentScope 和个人规则，决定是否以及如何授权 B，并完成人的任务验收。

“80% 以上”表示资源配置方向，不维护工时配额。代码复杂、状态机复杂或金融风险高都不自动触发 B；Core Oracle、反例和普通验证仍属于 A。分工继续附着在用户结果上，不建立 A/B 平行任务板。当前 WP0-1 至 WP0-4 的运行时已实现；具体外部来源语义仍按实际可用事实决定 Coverage。

### WP0-1：投资范围、规则与按问题判定的数据状态

**用户结果**：用户知道系统正在检查哪个账户/基金、按哪一版规则，以及每个问题能否判断；一个问题缺数据不会让整个复盘失效。

| 角色 | 工作 |
| --- | --- |
| Agent A | 定义 InvestmentScope、规则适用范围、JudgmentResult、按问题 Coverage 和 Ledger migration 边界；只依据已观察的来源事实，旧记录无法无损迁移时先提交迁移决策，不清库。 |
| Agent B（仅存在授权证据缺口时） | A 完成字段契约和人工场景后，如持仓、总资产/可投资分母、净值或交易状态的真实字段仍只能在授权来源中确认，则分目标验证其有无、日期、方向、确认语义、范围和 Coverage；只回传脱敏结论。 |
| 维护者 | 选择默认投资范围，定义个人规则语义和可接受的 unknown；不需要提供真实值给 Agent A。 |

**交接物**：A 先完成字段契约、迁移和静态排错；若仍存在授权证据缺口，B 才将真实环境观察到的 field presence/absence、semantic mapping、Coverage、unknown 和 Required change 脱敏回传给 A。任何阶段都不通过真实账户值交接。

**人的验收问题**：总资产未知时，我能否看见“仓位暂不能判断”，同时继续判断计划操作和移动止损？

**停止条件**：范围、分母、日期或来源语义只能靠猜；迁移会丢失既有本地记录；需要扩大真实环境授权。

### WP0-2：计划操作与真实执行对照

**用户结果**：用户能区分无操作、计划内操作、计划外/超量操作，以及待确认、部分确认、失败和撤销，不再把历史大额等同于异常。

| 角色 | 工作 |
| --- | --- |
| Agent A | 定义版本化 DecisionRecord/OperationPlan、不可覆盖的事前快照、execution lifecycle 和偏离维度；复用 Transaction、PolicyVersion、Ledger、Action，但不把 Action status 当成真实执行。 |
| Agent B（仅存在授权证据缺口时） | A 完成 execution mapping 后，如真实来源能否区分申请与确认、确认日期/金额/份额、失败/撤销/分页仍无法在非私人环境证明，才在授权的目标真实环境验证这些语义；不判断操作是否合理。 |
| 维护者 | 用人工计划场景确认“异常”理由是否符合自己的规则，而不是接受系统替其设定偏好。 |

**交接物**：真实来源状态能力 → execution mapping → 目标页面的理由与可核实证据引用。

**人的验收问题**：我能否准确说出某操作为何被标记——无计划、超计划、违反暂停规则，还是只有历史金额信号？

**停止条件**：申请与确认无法区分；事前记录可被事后覆盖；缺失关联时系统试图自动猜测。

### WP0-3：仓位、移动止损与减仓恢复

**用户结果**：用户知道仓位是否越界、止损线是否上移/触发、减仓真实进行到哪一步以及是否已恢复。

| 角色 | 工作 |
| --- | --- |
| Agent A | 建立可复算的 PositionJudgment、TrailingStopRule/State、ReductionPlan/Progress；实现分母 gate、止损线单调不降、陈旧 NAV 降级、部分确认和操作后恢复复算。 |
| Agent B（仅存在授权证据缺口时） | A 完成规则、计算和静态排错后，如净值日期及分红/复权语义、真实持仓/份额与确认状态仍是输入资格的关键未知，才在目标真实环境验证来源能力；只报告能力与缺口，不设计阈值、不评价是否该减仓。 |
| 维护者 | 事前定义仓位区间、止损阈值和减仓目标区间，并确认触发只表示待人处理，不是自动交易指令。 |

**交接物**：规则版本 + 人工事实 → 确定性状态和计算解释；真实来源能力只决定输入资格，不成为业务规则 Oracle。

**人的验收问题**：我能否从创新高、未创新高、陈旧净值和部分确认四个场景解释系统为什么上移、不动、unknown 或仍未完成？

**停止条件**：没有用户规则却生成阈值；止损线可下移；申请被当成确认；Action 关闭被当成仓位恢复。

### WP0-4：一页复盘与真实验收

**用户结果**：用户从“需处理 → 已符合 → 暂不能判断”完成本期检查，并从每个结论下钻到事实、规则版本、计算和缺失项。

| 角色 | 工作 |
| --- | --- |
| Agent A | 定义 `/investment/review` 的 P0 orchestrator、Query DTO 和页面；UI 不重算 Core，不按对象、Agent 或工程状态机组织首层信息。 |
| Agent B（仅存在授权证据缺口时） | A 的 Core、页面和普通验证完成，且维护者对一个明确主张单独授权后，才在用户真实 Chrome 中只读验证“同步 → facts → Coverage → judgment input → reload”的相应来源链和隐私边界；隔离 profile 不得替代真实验收。 |
| 维护者 | 执行下一节的 10 分钟人工审查，决定产品是否真的降低完整判断成本。 |

**交接物**：A 的完整实现、测试与页面证据；存在授权证据缺口且获批时，追加 B 的定点脱敏报告；维护者记录人的任务结果。三类证据不能互相替代，未启用 B 不等于 A 的非私人交付未完成。

**人的验收问题**：不理解 Agent 分工和领域对象的人，能否找到全部待处理偏离，并准确说出系统不能证明什么？

**停止条件**：页面以一个“系统正常”覆盖未检查规则；需要账户操作、扩大授权或记录敏感数据；真实 Chrome 无法接管时报告 `BLOCKED`。

## 7. 怎样证明它对人友好

### 10 分钟人工审查脚本

只使用人工构造的数据，不使用真实账户值：

1. **1 分钟：范围与规则**——指出系统正在检查什么范围、哪一版规则，单只基金与组合仓位有什么区别。
2. **2 分钟：操作对照**——分别解释无操作、计划内、无计划、超计划和暂停期新增；指出历史金额异常为何只是信号。
3. **2 分钟：仓位与独立 unknown**——识别仓位越界；移除总资产分母后，确认只有仓位判断降级，其他可回答问题仍保留。
4. **2 分钟：移动止损**——验证创新高时上移、未创新高时不动、陈旧净值时 unknown，且止损线永不下移。
5. **2 分钟：减仓恢复**——依次识别已计划、已申请、部分确认、已确认但仍越界和确认后恢复。
6. **1 分钟：边界**——说明系统没有替用户决定阈值、没有自动交易，也不能保证未来盈利。

### UX Gate

以下任一项失败，P0 不得标记完成：

- 首屏按金融对象、Agent 或指标组织，而不是按用户问题组织；
- 用户必须先补齐 Benchmark、现金流、FX 或税才能检查可独立回答的纪律问题；
- 一个缺失项把所有判断都变成 `INSUFFICIENT_DATA`；
- “正常”没有列明已检查的规则和未覆盖问题；
- 计划、申请、部分确认、确认、Action 关闭和恢复被混为一谈；
- 历史金额偏离被直接定义为操作异常；
- 止损线下移，或陈旧 NAV 仍推进状态；
- 用户看见偏离却不知道原因、证据和下一步；
- 页面诱导自动买卖、“盈利即正确”或“亏损即错误”。

人工审查记录场景、用户答案、耗时、误解点、是否需要外部计算和 Required change。通过脚本只证明任务可理解，不证明长期决策质量已改善。

## 9. 完成标准与核心反例

每个当前工作包都必须同时满足：

1. 输入、版本、Coverage、输出和失败状态有明确契约；
2. Core 只消费真实来源标准化事实，不依赖 LLM；其正确性须由目标真实环境的最终页面结果验收；
3. expected 来自手算、独立公式、性质/不变量或状态转换；
4. `normal/empty/partial/stale/failed/unknown` 有按问题可见的行为；
5. migration、reload、幂等和历史版本不丢失；
6. UI 能从结论下钻到事实、规则版本、Coverage、限制和下一步；
7. tests、typecheck 和 production build 结果如实记录；
8. 不引入真实基金名、金额、收益、Cookie、Token、Raw Snapshot、登录态或完整 Network Logs；
9. 通过对应人的验收问题和 10 分钟脚本；
10. 实现与匹配证据完成后才升级本文状态。

P0 至少覆盖这些人工反例：

- 规则内且本期无操作，只对已覆盖判断显示无需处理；
- 有计划且已确认；无计划、超计划和暂停期间新增；
- 仓位超限，以及分母缺失时只有仓位 unknown；
- NAV 创新高、未创新高、陈旧和分红/复权语义不清；
- 减仓已计划、已提交、部分确认、确认后仍未恢复和已恢复；
- 交易历史 partial 时只降级依赖完整历史的判断；
- 正收益但过程违规、负收益但过程合规；
- Benchmark 缺失不阻断 P0；跨币种/税务不适用时不进入前置清单。

详细对象、不变量和真实环境验收边界在[工程附录](reference/investment-review-engineering.md)中；它不是理解本次需求的前置材料。

## 10. 不可违反的边界

1. 用户的 InvestmentScope 和事前规则先于评价；没有规则时不发明合理仓位、止损或减仓。
2. 每个用户判断拥有自己的最小证据和状态；缺失不能无理由扩散为全局失败。
3. Decision 与 Execution 分开；计划、申请、部分确认、确认、失败、撤销和前后快照不能合并为 Action status。
4. 历史使用当时有效的 Policy、Rule、Decision、Benchmark 和 Profile 版本；当前编辑不回写历史。
5. 止损线只上移或不动；陈旧、partial 或 unknown NAV 不推进状态。
6. 减仓触发只生成待人处理事项；真实确认和操作后恢复必须分别验证。
7. Decision Quality 与 Outcome Quality 分离；收益不参与 P0 过程合规状态计算。
8. Target 与 Benchmark 分开；Benchmark 事前确定并版本化，不事后重选。
9. P1 的 TWR 与 MWR/XIRR 回答不同问题；现金、费用和外部现金流不能静默消失，不足一年不伪装成年化实绩。
10. Attribution 必须匹配数据能力；证据不足显示 residual/limitation，不制造 allocation、selection 或心理原因。
11. 行为 Finding 需要样本、阈值、反例和替代解释，不构成心理诊断。
12. AI 不计算核心指标、不预测市场、不改变规则或状态；重要陈述必须引用确定性证据。
13. Agent A 是主力交付角色，必须先完成契约、Core、迁移、UI、静态排错和修复，不得把这些工作转交 Agent B；完成结论必须来自经授权的目标真实环境操作，同时不得把真实账户、真实资产、交易、Cookie、Token、Raw Snapshot、登录态或完整 Network Logs写入仓库或交接材料。
14. Agent B 不是通用 reviewer，只在 A 已完成可完成工作、仍存在明确授权证据缺口且维护者单独授权时进入真实环境；它只输出脱敏 `PASS | FAIL | BLOCKED`、字段有无、Coverage、unknown、语义映射、Required change 和 Sensitive data exposed，不设计 Core 规则、不评价仓位或减仓、不执行账户操作，也不输出基金名、真实金额、收益、原始 JSON/HTML、Cookie、Token、银行卡信息、登录态或完整 Network Logs。
15. 真实登录环境是验收目标时，隔离 profile 不能替代用户真实 Chrome。
16. 系统不自动买入、卖出、申购、赎回、调仓、转账或交易。

- **规则理论依据可追溯**：新增 `engines/policy/rule-rationale.ts`，每类规则关联 [投资绩效与决策复盘理论框架](../theories/investment-performance-and-decision-review.md) 领域的理论概念（集中度风险/再平衡/移动止损/处置效应/过度交易/IPS 限额），并诚实标注阈值数值为风控惯例示例值；组合页每条配置参考可下钻"依据"（意图/理论/阈值依据），证据页设"规则与理论依据"卡，Context Package 规则段附依据。理论提供原则、不给具体阈值，与第 10 节"系统不发明合理仓位"边界一致。
- **组合页配置偏离决策闭环**：偏离项（超上限/低下限）不再止于提示，加三条决策路径闭合"看见→处理"——**认可偏离**（记录理由，localStorage 持久；认可 key 含规则区间参数，规则改后 key 变、旧认可自动失效，强制对新规则重新决策）、**调整规则**（单基金跳规则页带 `assetId/kind` 预填编辑区间、保存新版本）、**深度分析→GPT**（跳证据页生成 Context Package，该偏离一并带入）；认可后 ⚠ 降级为 ✓ 已认可+理由+可撤销。提示只降低认知成本，决策路径不断。

**未改变**：P0 纪律与执行复盘（操作合规、仓位、移动止损、减仓恢复）运行时状态；复盘路由与 ReviewView；规则/行动视图代码（保留，仅移出主导航）；第 10 节全部边界。相关 selector 的完成状态只以真实组合页面的实际结果为准。

### 12.3 默认规则集与第 10 节边界的调整

为降低"逐条声明阈值"的管理成本（用户反馈规则页 21 条逐条编辑太重），规则页改为**默认规则集优先**：`engines/policy/default-rules.ts` 提供基于 `rule-rationale.ts` 风控惯例的示例阈值（仓位 0–25% 目标 15%、移动止损 10%、目标止盈 20%、减仓目标 10–20%），用户一键采纳即生效，无需逐条填写；对某条有疑问可"疑问→深度分析"跳行动页生成 Context Package 交通用模型，据结论在自定义区调整或忽略。

这是对第 10 节"没有规则时不发明合理仓位"的**边界调整**（非违反）：默认值定位为"理论原则的量化惯例参考、非权威值、可外包分析后调整/忽略"，仍不声称是"合理仓位"或大师策略权威阈值；用户可随时自定义或重置。理论提供原则、默认值提供起点、外包分析提供深度判断、用户做最终接受/忽略——管理成本与边界诚实性兼顾。

### 12.4 历史周期场景压力测试（机构 scenario analysis 思路）

把当前真实采集持仓**平移到真实历史市场周期净值曲线**上做压力测试——A股对 A 股历史（2015 杠杆牛熊/2018 单边熊/2021 核心资产顶）、美股对美股（2008 金融危机/2022 加息熊）、黄金对 2020 避险牛——看该历史风格下组合的回撤、末态暴露与配置偏离。复盘页加"历史周期场景压力测试"卡（虚构模拟器与配置对比并存）。

- `engines/scenario/historical-cycles.ts`：6 段示意性周期，月度涨幅为基于公开历史的近似值，每段带 disclaimer。
- `engines/scenario/stress-test.ts`：`buildHistoricalStressTest` 以当前市值为基准平移（不模拟交易），重算回撤与末态暴露/偏离；未匹配周期基准的持仓（如 A 股资产在美股周期下）市值不变、标注 matched=false，不伪造收益。复用 `aggregateExposure`/`buildAllocationDrift`。
- 边界：示意性历史风格，**非精确回测**；平移非预测；不触碰真实账户（纯本地内存计算）。与第 10 节边界一致。
- 该卡片必须在实际部署页面用真实持仓操作，核对匹配/未匹配持仓、回撤、末态 drift、免责声明和失败状态；示意周期计算或构建成功不能替代验收。
- **一键操作反馈**：历史周期加 `buildAllCyclesStressTest` 一次跑完 6 段返回"最脆弱/最稳健场景"汇总（各周期回撤+末态偏离+最差资产）；牛熊演练加"一键跑完整周期"自动推进到末态。把"手动选周期/逐轮推进 + 逐层下钻"转为"一键运行 + 直接返回结论反馈"，降低操作与审查成本。
