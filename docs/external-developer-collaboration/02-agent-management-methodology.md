# Agent 管理方法论

本文是可公开交流的方法论，不是公司内部 Agent 管理模板的复制品。内部项目应根据权限、数据、合规和工具链进行适配。

## 1. 核心原则

### 1.1 上下文是维护资产

项目应把“当前事实”“为什么这样设计”“未解决问题”和“迭代证据”分开管理：

- **项目事实**：当前仍然成立的架构、入口、命令、数据流和约束；
- **决策记录**：重要选择、被拒绝的替代方案及原因；
- **业务说明**：当前用户能力和边界；
- **演进规划**：未来假设、阶段目标和验证指标；
- **迭代日志**：本轮范围、变更、验证证据和剩余风险。

不要让一个巨型文档同时承担所有职责。文档越接近维护场景，越应该回答“现在是什么”和“为什么”。

### 1.2 Agent 的工作边界应可审查

Agent 任务进入时应明确：

- 目标和完成条件；
- 已确认的事实；
- 明确不做的内容；
- 可能改变行为、兼容性、架构或不可逆操作的未解决问题；
- 需要留下的验证证据。

Agent 的内部推理不是审查对象。可审查对象是上下文、计划、代码差异、命令输出、浏览器证据和迭代记录。

### 1.3 先证据，后结论

事实来源优先级建议为：

1. 当前源码、配置和生成输出；
2. 项目上下文和已批准的决策；
3. 受影响区域的定向搜索；
4. 测试、构建和运行时证据；
5. 一般惯例或外部建议。

所有结论都应区分“已确认”“推断”和“未解决”。如果源码与文档冲突，以受影响路径的当前源码为准，并同步修正文档。

## 2. 推荐生命周期

```text
任务进入 → 建立基线 → 定向探索 → 最小实施 → 验证 → 记录风险 → 决定是否公开反哺
```

### 任务进入

先读取项目上下文和相关业务说明，确定影响范围。低风险、范围清晰的任务可以直接定向处理；跨模块、行为变化、依赖迁移、构建/部署或不可逆操作需要显式计划和回滚边界。

### 建立基线

写下任务目标、依据事实、完成条件、明确不做什么和未解决问题。基线不是形式化审批，而是防止 Agent 在执行中无声扩大范围。

### 定向探索

从用户指定的路径、直接消费者、测试入口和生成链开始。只在证据表明有影响时扩大范围。没有必要时不要重复全仓库发现，也不要为单文件低风险任务引入并行流程。

### 最小实施

保持现有行为和项目风格；不为了“顺手优化”增加抽象、依赖、自动钩子或无关重构。计划外变化应说明触发证据、影响范围和是否需要确认。

### 验证

验证记录至少说明：

- 运行了什么；
- 证明了什么；
- 跳过了什么以及为什么跳过；
- 仍不能证明什么；
- 剩余风险由谁负责。

首页 HTTP 200、单次静态检查或“代码看起来正确”不能替代受影响流程验证。

### 收尾

把短期风险记入迭代日志，把长期仍有效的事实或风险记入项目上下文。未验证项必须明确标记，不以“无剩余风险”作为默认结论。

## 3. 内部适配提示

公司项目采用本方法时，至少应补充以下内部约束，但不要把这些约束原样公开：

- 权限模型和人工确认点；
- 数据分类、隐私和留存规则；
- 可用工具、网络出口和凭据管理；
- 组织内审批、发布、回滚和责任人；
- 项目特有的构建、测试和部署命令。

公开方法论只保留“为什么需要这些边界”和“如何审查”，不公开具体组织配置。

## 4. 什么时候适合反哺开源

适合反哺的内容通常具有以下特征：

- 不依赖公司内部系统即可理解；
- 能通过公开示例、测试或文档复现；
- 对多个项目有类似收益；
- 不包含私有业务语义；
- 许可证和归属清晰；
- 已完成脱敏、技术审查和发布审批。

内部一次性修复、私有供应商适配、组织权限规则和包含真实数据的诊断结果，不应直接作为通用 PR 发布。
