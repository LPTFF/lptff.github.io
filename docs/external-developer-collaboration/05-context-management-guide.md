# 上下文管理机制：开发者可复制版

本文将本项目已经验证的上下文管理思路，整理成开发者可以复制到其他项目的公开机制。复制的是**文档职责、信息流和审查动作**，不是本项目的业务事实、内部权限或 Agent 配置原文。

## 1. 先复制什么

推荐从 [context-kit/](templates/context-kit/) 开始复制：

```text
AGENTS.md                         # Agent 通用工作流和升级条件
CLAUDE.md                         # 项目入口、命令、目录和验证规则
.claude/
├── project-context.md            # 当前仍有效的项目事实、决策和风险
└── iteration-log.md              # 每轮变更、证据和剩余风险
docs/
├── business-function-overview.md # 当前业务能力和边界
└── business-evolution-plan.md    # 未来规划、假设和验收标准
```

如果项目不使用 Claude Code，可以将 `AGENTS.md`、`CLAUDE.md` 替换为团队使用的 Agent 入口文件；`.claude/` 只是建议的目录名，机制本身不依赖特定工具。

## 2. 六类信息分别放在哪里

| 文件 | 负责回答 | 不应该放什么 |
| --- | --- | --- |
| `AGENTS.md` | Agent 如何进入任务、探索、实施和验证 | 频繁变化的项目事实、单次过程日志 |
| `CLAUDE.md` | 这个仓库如何运行、有哪些路径和命令 | 复杂决策历史、每次迭代的流水账 |
| `.claude/project-context.md` | 当前项目是什么、为什么这样设计、有哪些长期风险 | 普通过程、已失效事实、聊天记录 |
| `.claude/iteration-log.md` | 本轮改了什么、证据是什么、剩余风险由谁承担 | 下一轮仍需长期维护的全部事实 |
| `docs/business-function-overview.md` | 当前用户能做什么、不能做什么 | 未来愿望、技术实现细节 |
| `docs/business-evolution-plan.md` | 未来要验证什么、按什么阶段演进 | 把未实现规划写成已上线能力 |

职责边界比文件名更重要。小项目可以合并文件，但合并后仍要保留“规则、事实、当前业务、未来规划、迭代证据”的区分。

## 3. 最小落地步骤

### 第一步：建立项目事实

从源码、配置、命令和构建输出中整理当前事实，只写已经确认的内容。每条事实尽量包含来源或影响路径。例如：

```md
- 入口流程：`index.html` → `src/main.js` → `src/App.vue`。
- 构建命令会先生成摘要，再执行类型检查和生产构建。
- 未确认：旧部署脚本是否仍由任何人使用。
```

不要把“看起来应该如此”写成事实；不确定内容放到“未解决问题”。

### 第二步：写 Agent 工作规则

规则文件只保留跨任务仍然有效的行为要求：

- 先读上下文，再按影响范围定向探索；
- 小任务最小修改，不默认扩大范围；
- 行为、架构、依赖和部署变更需要更强验证；
- 说明运行了什么、证明了什么、跳过了什么和剩余风险；
- 不把 Agent 内部推理当作审查证据。

项目命令、目录、生成文件和技术栈放到 `CLAUDE.md`，不要在多个规则文件中重复维护。

### 第三步：建立业务基线和规划

先写当前业务能力，再写未来规划。对每项能力标记状态，例如“已实现”“演示”“待开发”或“外部跳转”。规划中的目标、假设和指标不能反向证明功能已经存在。

### 第四步：建立迭代日志

每轮新增一条可审查记录，至少包含：

1. 任务基线；
2. 实际变更和偏离控制；
3. 重要文件；
4. 验证证据；
5. 剩余风险、影响和责任人。

日志记录证据，不替代测试和代码审查。

### 第五步：把机制接入工作流

在每次任务开始和结束时执行固定动作：

```text
开始：读取 project-context → 明确基线和范围
执行：按影响区域探索 → 最小修改
结束：运行相关验证 → 更新 iteration-log
必要时：更新 project-context / 业务说明 / 演进规划
```

可以用脚本检查高影响文件是否同步更新上下文，但脚本只能提醒，不能自动判断业务事实或审批结果。

## 4. 什么时候更新哪个文件

- 新增或删除路由、目录、生成链、命令、依赖、部署路径：更新 `project-context.md`；
- 仅本轮有效的故障、验证结果和未完成检查：更新 `iteration-log.md`；
- 用户能力、入口或业务边界改变：更新 `business-function-overview.md`；
- 产品假设、阶段目标或验收指标改变：更新 `business-evolution-plan.md`；
- Agent 工作方式或验证门槛改变：更新 `AGENTS.md`；
- 项目命令、技术栈或目录说明改变：更新 `CLAUDE.md`。

同一事实只保留一个主要来源，其他文件通过链接或简短入口引用，避免复制后逐渐分叉。

## 5. 维护规则

### 事实生命周期

```text
源码/配置证据 → 当前事实 → 发生变化时更新 → 旧事实删除或改写
```

过时事实应删除，不要用“已废弃”长期堆积在当前上下文中；如果历史原因仍有价值，放入迭代日志或决策记录。

### 风险生命周期

```text
发现问题 → 记录未解决 → 验证或决策 → 写入当前事实/关闭问题
```

风险必须有影响范围和责任人。没有验证的事项不能写成“无风险”。

### 上下文预算

上下文文件应短而稳定：

- 规则文件只写长期规则；
- 项目上下文只写当前仍有效的高价值事实；
- 迭代日志按条目追加，不把所有历史重新塞回上下文；
- 大型数据、生成产物和完整日志不要直接写入上下文；
- 用路径、命令和证据摘要指向原始材料。

## 6. 如何适配公司项目

复制模板后，内部项目还需要自行补充：

- 权限和人工确认点；
- 数据分类、隐私、留存和脱敏要求；
- Agent 可用工具、网络出口和凭据管理；
- 内部审批、发布、回滚和责任人；
- 项目专用的构建、测试和部署证据。

这些内容可以存在于公司内部版本，但不应直接复制到公开仓库。对外反哺时，只提炼为组织无关的规则、示例或脚本，并使用 [脱敏与发布审批](03-sanitization-and-approval.md) 中的检查流程。

## 7. 复制后的验收清单

- [ ] 新成员能从入口文档找到开发、构建和验证命令；
- [ ] Agent 能知道先读哪些上下文、何时扩大探索范围；
- [ ] 当前业务能力和未来规划没有混写；
- [ ] 重要架构事实有单一来源；
- [ ] 每轮变更都能找到范围、证据和剩余风险；
- [ ] 未解决问题没有被伪装成已确认事实；
- [ ] 文档不含内部身份、凭据、真实数据或未公开决策；
- [ ] 团队知道何时更新上下文，且不会把日志无限复制到规则文件。
