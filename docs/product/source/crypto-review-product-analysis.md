## 1. 这是什么产品

加密货币复盘助手是个人加密货币合约交易的**纪律与重大错误防护工具**，不是行情看板、不是信号系统、不是自动交易机器人。

它首先帮助用户回答基金复盘那五个问题在合约语境下的重写：

1. 数据足以判断哪些问题，哪些还不能判断？
2. 本期开平仓操作是否符合自己事前的计划与规则？
3. 保证金率、距爆仓价安全距离、杠杆和方向暴露是否越界或需要处理？
4. 下单是否真实成交、平仓是否完成、是否发生爆仓？
5. 经过多个周期，结果是否支持保留或修改下一版规则？

产品扩展的是人的记忆、计算、比较和防爆仓警觉能力，不是鼓励增加杠杆。它可以帮助用户提高过程一致性和从重大错误中学习的能力，但不能保证持续赚钱，更不能保证不爆仓——爆仓风险只能由用户自身的纪律控制，产品只如实呈现距爆仓的距离和纪律偏离。

### 产品首要目标：防重大错误

基金复盘的首要痛点是"纪律偏离累积"，crypto 合约的首要痛点是**一次重大错误清零**。这决定了 P0 的重心不是绩效测量，而是：

- 保证金率是否逼近维持保证金线（防爆仓第一道防线）；
- 杠杆是否越过用户声明的上限；
- 单方向总暴露是否过度集中；
- 移动止损是否触发且距爆仓价是否仍有安全距离；
- 本期是否存在计划外的开仓/加仓/不平仓。

这些判断都不预测市场，只对照用户事前规则和当前事实。

## 3. 合约语境下的对象模型与纪律重写

### 3.1 对象模型对比

| 基金对象 | 合约对应 | 差异说明 |
| --- | --- | --- |
| Holding（份额+成本） | **Position**（多/空方向 + 杠杆 + 保证金 + 开仓价 + 爆仓价 + 未实现盈亏） | 基金持仓是持有资产，合约头寸是带方向和杠杆的暴露；同一币种可有多空两头寸 |
| Transaction（申购/赎回申请→确认） | **Order + 成交回报**（开仓/平仓单、市价/限价、全成/部分/未成交） | 基金交易是现金↔份额单向，合约是开仓↔平仓成对，平仓结清头寸 |
| NAV（T+1 净值） | **标记价格 + 资金费率**（8h 结算） | 行情近实时可得，但爆仓价依赖标记价与维持保证金率规则 |
| 无对应 | **Liquidation（爆仓事件）+ 维持保证金** | 基金不存在的毁灭性风险对象，是 P0 核心纪律对象 |
| 申赎费 | **手续费 + 资金费率 + 滑点** | 资金费率是长期持仓隐性成本 |

### 3.2 纪律问题的合约版

| 基金问题 | 合约版 | 成立性变化 |
| --- | --- | --- |
| 操作是否符合事前计划？ | 同——但合约高频，事前计划形态从"单笔计划"可能变为"信号触发开/平仓规则"，粒度待重设计 | 成立，形态变 |
| 仓位是否越界？ | **三口径**：①保证金占比（占用保证金/权益）②实际暴露占比（保证金×杠杆/权益）③单方向总暴露 | 基金只有一个市值占比；合约不区分这三口径会让杠杆掩盖真实暴露 |
| 移动止损是否触发？ | 止损线与**距爆仓价安全距离**强相关；触发不只看价格回撤，还要看保证金率是否逼近维持保证金线 | 语义变：基金止损是回撤控制，合约止损含防爆仓 |
| 减仓是否恢复？ | **平仓进度**：计划平仓量 vs 已平仓量 vs 是否仍越界 | 对应减仓恢复，对象是头寸 |
| 申请后是否真实确认？ | 下单是否成交、平仓是否完成、**是否爆仓** | 新增爆仓终止事件 |
| 多周期结果是否支持规则迭代？ | 同——但盈亏受资金费率和爆仓影响，口径更复杂 | 成立，成本口径增 |

### 3.3 默认规则集参数域（合约版，对齐基金 12.3 思路）

基金默认集（止损 10%、仓位 0–25% 目标 15%、止盈 20%）在合约语境**完全不适用**——10% 止损在合约杠杆下等于爆仓。合约版默认集候选，定位仍为"风控惯例参考起点、非权威值、可外包分析后调整"（与基金 12.3 边界诚实性一致）：

- 单仓杠杆上限（如 ≤5x，按币种波动分级）；
- 保证金率安全线（如 ≥50%，低于则预警，逼近维持保证金率则强制止损）；
- 单方向总暴露占比上限；
- 移动止损（按标记价，阈值按币种波动率分级，远小于基金）；
- 止盈/分批平仓目标。

理论依据（杠杆风险/维持保证金/凯利准则/资金管理）需在 `rule-rationale.ts` 的 crypto 版单独关联，诚实标注为示例值，理论提供原则、不给具体阈值。

## 4. 浏览器采集插件多资产升级

### 4.1 架构决策

不新建 crypto 专用插件，而是**升级现有 `lptff-investment-assistant` 插件支持金融多资产**，从单一基金扩展为"基金 + 加密货币"同一插件。理由：

- 采集→脱敏→协议化导入 Ledger 的链路已被基金验证，基础设施（manifest、popup、offscreen、脱敏下载、残留自检）复用价值高；
- 维护者同一人，多插件管理成本高于单插件多资产；
- 未来若再扩展资产类别（股票、外汇），同一插件可继续承载。

### 4.2 升级要点

| 模块 | 基金现状 | 多资产升级 |
| --- | --- | --- |
| 插件名/品牌 | investment-assistant | 保留或泛化为多资产语义，不阻断 |
| `source-capture.js` | 天天基金采集逻辑 | 按资产类型分发：基金 capture + 币安 capture |
| `content/` | 基金页面脚本 | 新增币安合约页采集脚本 |
| `rules/` | 天天基金页面匹配 | 新增币安页面匹配规则 |
| `public-fund-metadata.js` | 基金元数据 | 增加 crypto 元数据或泛化为 asset-metadata |
| `popup` | 基金采集入口 | 增加资产类型切换 |
| 脱敏自检 | 32 位交易/追踪 ID + 银行卡尾号零残留 | 新增 crypto 版清单：订单号、成交 ID、API 相关标识、钱包地址（若涉及划转）零残留 |
| 协议 | `eastmoney-source-capture/1.0` | 新增 `binance-source-capture/1.0`（或泛化多资产协议），导入链路复用 `toInvestmentDataset → SyncService` |

### 4.3 Ledger 与投资范围

本地 IndexedDB Ledger 需支持多资产 scope：基金 scope（`scope:real-account`）与 crypto scope 并存或统一为多资产投资范围。仓位/暴露/规则判断按 scope 隔离，避免基金与 crypto 规则混淆。具体 scope 模型待工程评估，但产品上"基金复盘"与"crypto 复盘"应可分别进入，不强行合并为单一总账（除非维护者声明统一投资范围）。

## 5. P0 候选切片（对齐基金 WP0-1~WP0-4 结构）

| 工作包 | 用户结果 | 关键差异 |
| --- | --- | --- |
| WP0-1 合约事实采集与标准化 | 用户知道系统在检查哪个交易所/哪些头寸、按哪版规则，每个问题能否判断 | 插件采集币安合约页 → 脱敏 → Ledger；adapter 重写（头寸/成交/资金费率/权益字段） |
| WP0-2 头寸纪律 | 用户知道保证金率/距爆仓安全距离/杠杆/方向暴露是否越界，止损是否触发 | 三口径仓位、维持保证金线、标记价移动止损——基金没有的新判断 |
| WP0-3 开平仓操作对照 | 用户能区分计划内/计划外开平仓、未成交、部分成交 | 合约高频语境下事前计划形态待重新设计 |
| WP0-4 一页复盘 | 从"需处理→已符合→暂不能判断"完成本期检查，下钻到事实/规则/Coverage | 复用基金三栏结构与图表/明细核对模式 |

P0 首要交付 WP0-2 的"防爆仓三判断"（保证金率/杠杆越界/距爆仓安全距离），因为这是"防重大错误"目标的最直接落地；WP0-1 事实采集是前提；WP0-3 操作对照在合约高频语境的形态待维护者裁决后再定。

## 6. 不可违反边界（合约版强化）

沿用基金第 10 节，并因合约特性强化：

1. **不自动交易**——合约可通过 API 真实交易且毁灭性更快，边界要更硬：插件**只采集、只读**，绝不写入下单/平仓/调保证金操作；
2. **不做市场预测**——不输出权威买卖建议，不预测爆仓概率，不预测价格方向；
3. **爆仓风险只如实记录**——只记录已发生的爆仓事件与当前距爆仓价距离，不预测爆仓；
4. **资金费率/滑点如实记录不优化**——作为成本事实，不作为"可优化收益"误导；
5. **脱敏自检清单（crypto 版）**——订单号、成交 ID、API 相关标识、钱包地址零残留，对齐基金 32 位 ID 零残留思路；
6. **只读边界**——即使未来引入 API key 通道，也强制只读权限，资金权限 key 一律拒绝；
7. **深度分析外包不内置**——Context Package 只输出带来源分层的事实+规则+缺口，不内置分析结论，不调 LLM，不自动外传；外部模型必须自行补充生成时点之后的行情与宏观。

## 7. 风险与剩余 unknown

- **合约采集 DOM 稳定性**：币安合约页是 SPA，字段随改版变动，adapter 需容忍字段缺失并降级为 unknown（对齐基金 Coverage 思路）；
- **合约 P0 工作量显著高于现货**：爆仓/保证金/资金费率是全新对象，不是基金的参数调整，是新建领域模型；
- **插件采集 vs 公开 API 取舍**：选插件采集沿用已验证链路、规避 key 安全/跨域问题，代价是行情实时性依赖页面刷新频率，资金费率历史/爆仓历史等可能页面不完整展示，需评估 Coverage 边界。

### 待人裁决的剩余问题

- **U-Plan 合约事前计划形态**：基金的事前计划是"单笔 DecisionRecord"，合约高频语境下事前计划更可能是"信号触发开/平仓规则"或"时段聚合口径"，具体形态待维护者声明自己的实际计划方式后再定；未定前 WP0-3 可先降级，不阻断 WP0-2 防爆仓判断。
- **U-Scope 投资范围模型**：基金与 crypto 是否合并为统一多资产投资范围，还是各自独立 scope，待维护者声明。
- **U-Rule 默认规则集参数**：合约默认阈值的具体数值需结合维护者实际交易的币种波动率分级确定，本文只给方向不给权威值。

## 8. 与基金复盘助手的衔接

本诉求不修改基金复盘助手的产品正文与 P0 状态。基金 `src/investment` 的 domain/engine 是基金语义（单币种、申请/确认状态机、NAV 日期），多币种与即时成交是硬差异，**直接复用代码前需工程评估**；方法论层 100% 可迁移。新产品建议在 `src/investment` 下按 scope 扩展（如 crypto scope 的 domain/engine/adapter），或在独立目录建 crypto 领域代码共享 Ledger/图表/Context Package 基础设施——具体工程结构待审查后定。
