# 项目业务演进与执行计划

> 文档版本：2026-07-26
> 文档性质：产品规划、当前任务看板和阶段验收依据。
> 当前能力基线：[业务功能说明](business-function-overview.md)
> 历史事实与验证证据：[迭代日志](../.claude/iteration-log.md)

本文只维护“未来要做什么、当前做到哪一步、怎样判断完成”。当前已经实现的路由、页面和功能，以 [业务功能说明](business-function-overview.md) 为准，不在本文重复维护完整功能清单。

本轮产品方向已从“个人综合信息工作台持续扩展”收敛为“利用私人数据，持续改善重要决策的个人高收益软件”。现有资讯、导航、学习和投资页面是能力基线与数据入口，不等于最终产品定位；后续投入必须优先服务于记录、分析、改进、验证的真实闭环。

### 产品方向判断标准

一个需求只有同时满足多数以下条件，才进入产品规划：

1. 高频使用，或在关键时刻反复使用；
2. 能影响金钱、职业、健康或大量时间；
3. 能积累个人数据，而不是只搬运外部信息；
4. 能形成“记录 → 分析 → 改进 → 验证”的反馈闭环；
5. 使用越久，个人模型和决策质量越有价值。

### 核心产品抽象

后续不先建设通用 AI 壳或复杂多 Agent 系统，而是围绕一个可验证的个人决策复盘模型演进：

```text
目标 → 信息 → 判断 → 行动 → 预期 → 结果 → 错误归因 → 修改规则
```

第一落点是交易复盘；模型中的交易字段、规则和指标只有在真实使用中稳定后，才抽象为可复用的“个人决策复盘引擎”。

每个产品任务都遵循项目的[可审查开发生命周期](../AGENTS.md)：审查任务基线是否明确、行为偏离是否受控、验证证据是否充分、剩余风险是否有责任人；不以 AI 的内部思维过程作为验收依据。

## 状态核验规则

- 运行行为和可复现验证结果优先于文档描述；
- 当前源码优先于旧计划；
- 迭代日志和提交记录用于补充实施证据；
- 无法通过源码或验证确认的事项，标记为“待核验”，不得直接标记为“已完成”；
- 每次迭代只需要更新：执行摘要、当前任务、任务看板、完成证据和状态变更记录。

### 任务状态

| 状态 | 含义 |
| --- | --- |
| 待核验 | 可能已有实现，但完成情况尚未核实 |
| 待开始 | 范围和完成标准已明确，尚未实施 |
| 进行中 | 已开始实施，但未满足全部完成标准 |
| 阻塞 | 存在明确的外部依赖或未解决决策 |
| 已完成 | 完成标准全部满足，并有证据 |
| 暂时跳过 | 当前有意不投入，保留恢复条件 |
| 已取消 | 已决定不再实施，并记录原因 |

### 产品假设状态

| 状态 | 含义 |
| --- | --- |
| 假设 | 尚未验证 |
| 验证中 | 已有实现或使用观察，但证据不足 |
| 已验证 | 指标和实际反馈支持继续投入 |
| 已否证 | 证据不支持原假设 |

任务执行状态和产品假设状态分开维护。例如，导航实验可以是“暂时跳过”，但“常用入口能否减少查找成本”仍然是“验证中”。

### 当前决策

首页导航专区已经使用 `localStorage.frequentWebsites` 按 URL 累计点击次数并生成“常用”入口。这个低成本实现先保留，不继续增加导航埋点、最近使用、任务分类或管理功能。

产品主线不再是把现有信息入口扩展成更大的门户，而是验证私人数据能否持续改善高影响决策。当前先选择交易复盘作为首个真实场景：投资页面的数据可信度是前置基础，交易前计划、执行结果、错误归因和规则修改构成后续闭环。职业资产与健康精力作为第二、第三方向保留，不与交易主线并行建设。

下一项工作转向投资页面的数据可信度。交易前计划记录必须等数据来源、时间和失败状态可解释后再开始，避免把不可信的数据快照保存成决策依据。

## 1. 当前任务

<a id="inv-data-001-投资数据可信度基础"></a>

### `INV-DATA-001`：投资数据可信度基础

| 项目 | 内容 |
| --- | --- |
| 所属阶段 | 阶段 0：证据与投资数据可信度基础 |
| 优先级 | P0 |
| 状态 | 待开始 |
| 前置依赖 | 核验现有投资数据文件、生成时间字段和页面加载逻辑 |
| 首批页面 | `FundPilotPlus.vue`、`Cryptocurrency.vue` |
| 后续任务 | `INV-DATA-002`、`INV-PLAN-001` |

#### 要解决的问题

当前投资页面已经局部显示“数据更新于”，但不同数据集的来源、生成时间读取方式、过期判定和加载失败反馈并不统一。只显示一个时间，不能让用户判断：

- 这份数据来自哪里；
- 它是什么时候生成的；
- 它是否已经过期；
- 页面当前显示的是新数据、旧快照还是空数据；
- 多个数据集只有一部分加载成功时，哪些内容仍然可用。

#### 本轮范围

1. 列出首批页面实际使用的数据集和来源；
2. 定义数据集标识、来源、生成时间和加载状态；
3. 定义最新、过期、时间未知、请求失败和结构异常状态；
4. 在基金分析 Plus 和加密货币页面持续展示这些状态；
5. 保留已有数据的情况下，刷新失败不清空旧数据；
6. 对多数据集页面分别显示状态，不用一份较新的时间掩盖另一份旧数据；
7. 验证正常、过期、时间缺失、请求失败四类场景。

#### 明确不在本轮范围

- 交易前计划与理由记录；
- 保存交易决策快照；
- 交易执行结果和交易后复盘；
- 接入基金或加密货币交易账户；
- 自动买入、卖出、转账或跟单；
- 账号、云端同步和远程埋点；
- 修改后端数据生产协议；
- 扩展首页导航能力。

#### 完成标准（Definition of Done）

- [ ] 已列出首批页面涉及的每个数据集及实际来源；
- [ ] 已定义数据集标识、来源、生成时间和加载状态；
- [ ] 已定义时间缺失、时间无效、最新和过期规则；
- [ ] 页面能直接显示数据来源、生成时间和当前可信状态；
- [ ] 请求失败、解析失败或必要结构缺失时有持续可见反馈，而不是只记录控制台日志；
- [ ] 已有旧数据时刷新失败不会清空旧数据，并明确标记旧快照；
- [ ] 多数据集页面拥有独立状态和清晰的页面汇总规则；
- [ ] 已验证正常、过期、时间缺失、请求失败四类场景；
- [ ] 已记录修改文件、验证结果和遗留限制；
- [ ] 未引入交易账户、远程数据存储或交易执行能力。

#### 完成证据

实施时在本节补充：

- 代码文件和关键实现；
- `npm run typecheck`、`npm run build` 结果；
- 浏览器正常及异常场景验证结果；
- 未解决问题和后续任务。

## 6. 产品方向与核心假设

### 6.1 交易判断与复盘（第一主线）

- **问题**：现有投资页面主要展示外部数据、策略和结果，不能持续回答“为什么做、是否按规则做、结果来自哪里、下次如何改进”；单纯盈亏展示无法区分能力、运气和风险暴露；
- **核心假设**：以交易复盘为首个真实场景，先保证数据可信，再用最小记录捕捉目标、信息、判断、行动、预期和结果，能够减少事后遗忘并发现可修正的错误模式；
- **假设状态**：验证中；
- **当前任务**：`INV-DATA-001`；
- **演进顺序**：

```text
外部数据可见
  → 数据来源和新鲜度可判断
  → 交易前目标、信息、判断、行动和预期可记录
  → 执行结果与计划自动/手动对应
  → 结果偏差和错误归因可复盘
  → 修改规则并在下一次行动中验证
  → 多次记录后区分收益来源、回撤来源和策略稳定性
```

- **第一版记录原则**：不接交易账户，不自动下单，不要求完整流水；优先支持手动记录一条决策，并保存当时引用的数据快照、规则版本和预期周期；
- **验证指标**：有效记录次数、交易前记录覆盖率、计划与执行的对应完整度、复盘完成率、重复错误出现次数、规则修改后的执行情况、回撤来源可解释比例；收益率只作为结果字段，不能单独证明产品有效；
- **阶段决策规则**：如果用户只看行情不记录判断，减少信息展示并降低记录摩擦；如果记录但不复盘，优先增加结果提醒和轻量归因；如果复盘后没有修改行动或规则，说明分析尚未形成闭环；如果规则在多次记录中无法改善执行或风险，降级为观察工具；加密货币维护成本高且使用频率低时，保留为实验数据源，不阻塞基金主流程。

### 6.2 职业资产系统（第二主线候选）

- **问题**：代码方案、项目成果和解决问题的案例分散在博客、面试资料和工作记录中，难以在真实工作、面试、跳槽和谈薪时快速复用；
- **核心假设**：围绕“问题—约束—方案—结果—证据—可复用表达”沉淀职业资产，比继续增加普通文章或待办更能积累长期职业资本；
- **假设状态**：假设；
- **启动条件**：交易复盘完成至少一轮真实闭环，且出现明确的职业场景需求；不与交易主线同时建设完整模块；
- **最小闭环**：记录一个真实项目问题 → 关联代码/文章/方案 → 记录结果和证据 → 在工作或面试中复用 → 复盘表达是否有效；
- **验证指标**：案例复用次数、限定时间内找到证据的成功率、解决方案被再次采用的次数、面试表达准备时间、谈薪材料完整度；
- **非目标**：不先建设大规模知识图谱、通用笔记软件或普通日报。

### 6.3 健康精力系统（第三主线候选）

- **问题**：睡眠、饮食、运动和工作状态会影响长期工作能力，但现有项目没有个人数据记录和可验证反馈；
- **核心假设**：从低负担记录开始，逐步分析精力与工作表现的关系，能够帮助保护长期工作能力；
- **假设状态**：假设；
- **启动条件**：职业资产方向已证明用户能持续记录，且健康场景的隐私边界、数据来源和解释责任已明确；
- **最小闭环**：记录精力与关键行为 → 标记工作状态 → 观察可重复关系 → 调整一个行为 → 验证下一周期结果；
- **验证指标**：记录持续率、行为与状态的可解释关联、调整后的复测结果、异常数据比例；不把相关性直接解释为医学因果，不提供诊断或治疗建议；
- **非目标**：不接入高敏感健康数据，不做医疗诊断，不做没有验证反馈的 AI 建议。

### 6.4 通用个人决策复盘引擎（长期抽象）

- **问题**：交易、职业和健康决策表面不同，但都可能遵循目标—信息—判断—行动—预期—结果—归因—规则的结构；过早抽象会制造通用表单和复杂配置，反而降低真实使用率；
- **核心假设**：至少一个具体场景完成闭环后，再提炼共享数据结构、复盘流程和指标，能够以较低成本支持第二个高价值场景；
- **假设状态**：假设；
- **启动条件**：`INV-REVIEW-001` 和至少一个后续改进验证完成；
- **抽象内容**：决策记录、证据快照、预期与结果对照、错误归因、规则版本、复盘提醒和验证结果；场景特有字段保留在领域模块，不为了统一而抹平差异；
- **非目标**：不为 Agent 而设计复杂多 Agent 系统；AI 只能辅助提取、归类和提出可审查问题，不能替代记录者的判断，也不能在没有反馈验证时自动给出权威建议。

### 6.5 高频入口与知识沉淀（支撑方向）

- **问题**：导航和知识内容能减少查找成本，但本身不一定改变重要决策；
- **处理原则**：现有导航和博客保留为入口与数据来源，只有出现可量化的查找/复用问题才扩展；知识关系优先服务职业资产和交易复盘，不单独建设“信息越多越好”的平台；
- **假设状态**：验证中/假设，按具体实验更新；
- **决策规则**：不能证明减少查找时间、提高复用率或改善决策的功能，不进入 P0。

## 7. 产品边界与非目标

当前项目正在从“面向个人使用的信息与决策辅助工作台”演变为“利用私人数据持续改善重要决策的个人高收益软件”。现有资讯、导航、博客、面试和投资页面继续作为入口、内容资产和数据来源，但不再以扩展信息覆盖面作为主要目标。

当前明确不做：

- 通用聊天壳、只有问答没有行动反馈的 AI 功能；
- 普通待办、日报、摘要和只有仪表盘没有行动改变的数据展示；
- 为 Agent 而设计的复杂多 Agent 系统；
- 基金或加密货币自动交易、自动跟单、转账；
- 托管用户资产或保存第三方交易凭据；
- 账号、权限、订阅、收费和云端同步；
- 评论、私信、社区协作和没有明确个人闭环支撑的社交能力；
- 没有使用证据支撑的大规模路由重构、服务化或平台化；
- 健康诊断、治疗建议和未经验证的高敏感数据推断。

产品长期边界是：只保存实现个人决策闭环所需的最小数据；默认本地优先，涉及私人数据的远程同步、埋点、分享或外部复用必须单独评估隐私、数据可携带性、删除方式和责任边界。

投资页面的策略、金额、评分和收益字段均为展示和个人辅助判断信息，必须保留数据时间、来源和风险边界。外部行情、iframe、第三方数据和外部链接不保证持续可用。职业资产是个人工作和表达辅助，不替代真实项目证据；健康精力分析不构成医学判断。

## 9. 验证指标与决策规则

每一轮实施至少记录：

| 项目 | 要回答的问题 |
| --- | --- |
| 问题 | 当前要解决的具体问题是什么？ |
| 假设 | 为什么相信最小实现可能有效？ |
| 最小实现 | 本轮明确做什么、不做什么？ |
| 观察指标 | 用什么判断有效或无效？ |
| 实际反馈 | 使用数据、主观感受和失败案例是什么？ |
| 决策 | 保留、优化、合并、降级还是删除？ |
| 下一假设 | 下一轮要验证什么？ |

### 个人高收益软件的统一验收问题

每个候选功能必须回答：

1. 使用频率是每天、每周、每月，还是只在偶发事件中使用？
2. 它影响金钱、职业、健康或大量时间中的哪一项？影响证据是什么？
3. 记录的私人数据是什么，是否会随时间增加价值？
4. 记录之后会产生什么分析，分析会改变什么具体行动？
5. 改变后的行动如何在下一周期验证？
6. 如果连续使用三到五次仍没有改变行动或解释结果，是否应降级或删除？
7. 是否能本地优先运行，数据删除、导出和隐私边界是否清楚？

### 方向优先级

| 方向 | 当前判断 | 进入开发的条件 | 暂不投入的理由 |
| --- | --- | --- | --- |
| 交易复盘 | **P0，第一主线** | 数据可信度完成，且能用最小记录验证一条决策闭环 | 需控制金融数据解释和自动交易边界 |
| 职业资产 | P1，第二主线候选 | 交易闭环稳定后出现真实项目/面试/谈薪需求 | 先避免建设普通知识库 |
| 健康精力 | P2，第三主线候选 | 记录习惯、隐私边界和非医疗解释责任明确 | 数据敏感，不能先做无反馈建议 |
| 通用复盘引擎 | 暂不实施 | 至少一个领域完成闭环并识别稳定共性 | 过早抽象会变成通用表单 |
| 导航/资讯扩展 | 支撑能力 | 有明确查找成本和可量化实验 | 信息展示本身不形成决策复利 |
| 通用聊天/多 Agent | **明确不做** | 除非服务于已验证闭环且有可审查反馈 | 没有反馈验证时只增加复杂度 |

功能投入规则：

- 高频且能改善真实决策：优先投入；
- 高频但只是信息搬运：优先自动化或简化，不继续堆功能；
- 低频但能沉淀长期资产：小成本保留并观察；
- 低频、低价值且维护成本高：降级或淘汰；
- 只有猜想、没有使用证据：不得直接扩展成大模块；
- 不能进入“记录—分析—改进—验证”闭环的功能，不作为核心产品方向。

## 10. 状态更新流程

每次迭代完成后按以下顺序更新：

1. 核对当前源码和运行行为；
2. 更新“30 秒执行摘要”的当前阶段、任务、状态和下一步；
3. 更新当前任务的完成标准；
4. 更新任务看板状态和依赖；
5. 满足完成条件后，将事项移入“已完成事项与证据”；
6. 如果暂停，移入“暂时跳过、阻塞与取消事项”，写明原因和恢复条件；
7. 在 `.claude/iteration-log.md` 记录范围、证据、文件、验证和未解决问题；
8. 运行项目规定的上下文检查，确认长期事实是否需要同步。

### 状态迁移

```text
待核验 → 待开始 → 进行中 → 已完成
                    ├→ 阻塞 → 进行中
                    └→ 暂时跳过 → 待核验
待开始 → 已取消
```

暂时跳过的任务恢复时先回到“待核验”，不直接恢复旧的“进行中”，因为源码和产品优先级可能已经变化。

## 当前版本结论

现在不是继续增加入口，也不是直接开发交易记录，而是先完成一个可以明确验收的任务：

> **让基金分析 Plus 和加密货币页面能诚实地告诉用户：数据来自哪里、什么时候生成、是否过期、加载是否成功。**

完成 `INV-DATA-001` 后，才进入交易前计划与理由记录。导航的常用入口能力保留现状，等再次出现明确的查找效率问题后再重新核验。
