# 项目业务功能说明与演进规划

> 文档版本：2026-07-26  
> 文档性质：基于当前源码的业务基线，以及面向后续迭代的产品规划文档。  
> 核心方法：假设 → 实现 → 使用 → 反馈 → 校准 → 决策。

本文是项目的**规划与实施依据**，与只描述当前能力的 [业务功能说明](business-function-overview.md) 分开维护：

- `business-function-overview.md`：记录当前源码、路由、导航和数据形态已经支持的业务基线；
- 本文：记录待验证假设、阶段目标、指标、实施顺序和决策规则。

未来规划中的内容必须标记为“假设”“验证中”或“已验证”，不得与当前已实现能力混写。

## 1. 文档目的

本文用于回答以下问题：

- 当前功能分别解决什么真实问题？
- 哪些能力应该优先服务站点所有者本人？
- 哪些功能值得继续投入，哪些功能只保留为辅助入口？
- 如何通过真实使用和反馈验证产品假设？
- 当短期收益和长期价值冲突时，如何做出取舍？

每轮迭代遵循：

```text
发现真实问题
  → 提出最小产品假设
  → 实现可使用版本
  → 观察本人和公开用户的使用行为
  → 收集反馈与失败案例
  → 判断保留、改造、合并或淘汰
  → 进入下一轮假设
```

## 2. 产品演进原则

### 2.1 个人价值优先，商业价值后置验证

当前项目没有注册、权限、订阅和多用户配置体系，因此第一阶段不以平台化或收费为目标。优先顺序为：

```text
个人真实收益
  > 高频使用效率
  > 可沉淀的数据和方法
  > 可被他人复用的能力
  > 商业化验证
```

商业价值不是独立新增的目标，而是个人工具持续使用后自然出现的外部复用机会。

### 2.2 沿现有业务逻辑演进

现有项目已经形成四类业务：信息聚合、常用导航、学习知识、投资信息辅助。后续优先改善已有闭环：

1. 先改善数据质量、使用路径和反馈记录；
2. 再合并重复页面和统一业务模型；
3. 最后才考虑账号体系、云端同步、对外服务或收费模式。

不在缺少使用证据时进行大规模路由重构、服务化或平台化建设。

### 2.3 用价值、频率和不确定性管理投入

| 维度 | 核心问题 |
| --- | --- |
| 现实价值 | 是否减少损失、节省时间或改善决策？ |
| 使用频率 | 是否每周或每月反复使用？ |
| 长期价值 | 是否沉淀数据、方法、内容或可复用能力？ |
| 不确定性 | 当前最需要验证的假设是什么？ |

功能优先级不是永久等级，应随验证结果变化。

## 3. 当前产品基线

当前项目是一个面向个人使用的综合信息工作台，已经包含：

1. 信息浏览和外部内容聚合；
2. 常用网站和站内功能导航；
3. 技术学习、博客和求职准备资料；
4. 基金、加密货币和策略结果的信息辅助；
5. 外部行情、购买、招聘和原文页面的快捷跳转。

当前最准确的业务判断是：

> 一个由个人高频需求驱动、正在从信息门户向个人决策与效率工作台演进的项目。

网站目前仍是信息展示、辅助判断和外部跳转平台：

- 不是基金或加密货币交易系统；
- 不执行买入、卖出、转账或自动跟单；
- 不托管用户资产；
- 不提供正式招聘投递闭环；
- 不提供评论、私信、社区协作或订阅服务；
- 不保证外部站点、行情 iframe 和第三方数据持续可用。

投资页面中的策略、金额、评分和收益字段属于展示和个人辅助判断信息，必须持续保留数据时间、来源和风险边界。

## 5. 核心演进方向

### 5.1 投资信息与交易辅助

#### 当前能力

现有投资业务包括：

- 基金买入建议；
- 基金持仓分析；
- 基金分析 Plus 和 V1；
- 加密货币持仓、推荐和候选分析；
- 行情 iframe；
- 外部购买和交易平台跳转；
- 筛选、排序、批量跳转和 Excel 导出。

当前已经形成：

```text
读取数据 → 查看策略 → 筛选比较 → 查看行情 → 外部操作或导出
```

#### 第一阶段假设

> 如果把分散的投资数据、策略结果和外部行情集中到一个工作台，是否能帮助个人更稳定地完成投资判断、执行记录和事后复盘？

重点不是增加更多投资信号，而是验证数据集中、记录和复盘是否改善个人决策过程。

#### 演进顺序

```text
数据可见
  → 交易前判断可追踪
  → 交易执行可记录
  → 交易后结果可复盘
  → 策略效果可验证
  → 风险控制可量化
```

优先改善：

- 数据更新时间和来源统一；
- 交易理由和计划记录；
- 实际执行结果记录；
- 策略建议与实际收益对照；
- 持仓集中度和风险暴露；
- 月度、季度复盘。

#### 验证指标

- 每周打开次数；
- 是否在交易前使用；
- 是否记录交易理由；
- 是否在交易后完成复盘；
- 策略建议被采纳、拒绝或忽略的比例；
- 数据错误、过期和无法解释的次数；
- 是否减少重复、冲动或计划外交易。

收益率不能作为唯一指标。短期收益可能来自市场运气，不能直接证明产品有效。

#### 反馈与决策规则

- 只看行情、不看策略：减少重复策略展示，强化筛选和风险信息；
- 看策略但不记录执行：增加轻量记录，而不是继续增加策略；
- 多个基金页面使用路径高度重复：合并为统一投资分析模型；
- 策略长期无法通过历史或实际结果验证：降级为实验信息；
- 加密货币使用频率低且维护成本高：保留个人实验状态，不影响基金主流程。

### 5.2 生活与工作高频工具汇总

#### 产品假设

> 如果将个人每天或每周反复访问的网站、搜索方式和内部工具统一组织，并根据真实使用频率动态排序，是否能减少重复查找和信息切换成本？

核心不是收集更多网站，而是验证：

- 哪些入口真的高频；
- 哪些入口属于同一个工作任务；
- 哪些入口应该被自动化或直接内置；
- 哪些内容只是噪音。

#### 演进重点

- 按任务而不是按网站分类；
- 高频入口置顶；
- 记录最近使用和常用路径；
- 为高级搜索保存常用模板；
- 将重复外部跳转逐步变成站内小工具；
- 为数据快照增加更新时间和失败提示。

#### 验证指标

- 每个入口的点击次数；
- 从首页到目标工具的步骤数；
- 高频入口的重复访问率；
- 搜索模板的复用次数；
- 外部跳转失败率；
- 访问后是否继续使用目标服务；
- 主动新增、删除或调整入口的次数。

### 5.3 技术学习与知识沉淀

#### 产品假设

> 如果把个人工作经验、面试知识、项目案例和技术文章组织成可检索、可复用的知识系统，是否能提升工作决策、面试表达和长期能力积累？

#### 演进重点

- 将文章、面试题和真实项目建立关联；
- 为内容增加场景、难度、技术栈和复用状态；
- 记录阅读、复习和项目应用结果；
- 将通用面试资料逐步转为个人真实经验；
- 将 GitHub Trending 收敛到前端、AI、自动化工作流等方向。

#### 验证指标

- 内容搜索和复用次数；
- 面试题与项目案例的关联次数；
- 文章被实际工作引用的次数；
- GitHub 项目被收藏、试用或纳入工作流的次数；
- 是否能在限定时间内找到所需知识。

## 6. 阶段性实施路线

### 阶段 0：业务基线和使用观测

**目标**：不急于增加功能，先确认真实使用路径。

**最小实施范围**：

- 统一统计页面和入口使用次数；
- 记录投资页面的查看、导出和外部跳转行为；
- 记录导航入口的新增、删除和重复使用；
- 标记数据更新时间、来源和失败状态；
- 清理重复页面和无法说明用途的入口。

**阶段出口**：能够回答“我每周真正使用什么、在哪一步退出、哪些信息没有帮助”。

### 阶段 1：个人投资决策闭环

**目标**：让投资模块从“展示建议”升级为“判断—记录—复盘”。

**优先能力**：

- 资产与持仓总览；
- 统一基金和加密货币数据模型；
- 交易前计划与理由；
- 交易结果记录；
- 策略建议和实际结果对照；
- 风险和集中度提示；
- 月度复盘。

**阶段出口**：个人能够持续使用，并能从历史记录中发现行为和策略问题。

### 阶段 2：个人高频工作台

**目标**：减少日常查找和信息切换成本。

**优先能力**：

- 任务型导航；
- 工作、投资、学习和生活分区；
- 常用搜索模板；
- 最近使用和常用入口；
- 高频外部服务的轻量内置工具；
- 外部数据失败和过期降级。

**阶段出口**：网站成为稳定的个人入口，而不是偶尔访问的信息集合。

### 阶段 3：知识资产沉淀

**目标**：把工作经验和个人方法转成可检索、可复用内容。

**优先能力**：

- 项目—技术—文章关联；
- 投资复盘和技术复盘；
- AI/前端/金融科技专题；
- 可复用模板和工作流；
- 个人经验与公开资料区分。

**阶段出口**：内容可以支持工作、面试、学习和未来产品验证。

### 阶段 4：外部复用验证

**目标**：验证哪些个人能力对其他人也有价值。

只选择已在个人使用中验证过的能力进行开放：

- 投资记录和复盘模板；
- 前端或 AI 工作流工具；
- 技术知识库结构；
- 数据分析和导出能力。

这一阶段才评估公开用户、模板、服务或 SaaS 可能性，不预先承诺商业化结果。

## 7. 第一轮落地清单

当前先落地规划文件，业务代码按后续迭代逐项实施。下一轮建议从以下 P0 范围开始：

### P0：使用观测与数据可信度

- [ ] 新增本地使用记录工具；
- [ ] 记录首页栏目切换和导航点击；
- [ ] 记录投资页面打开、筛选、导出、刷新和外部跳转；
- [ ] 统一投资数据的更新时间、来源和失败状态；
- [ ] 支持查看和导出当前设备的使用记录；
- [ ] 保持数据只存储在当前浏览器，不引入账号和远程埋点。

### P0：投资交易前记录

- [ ] 增加交易前计划记录；
- [ ] 保存当时的策略和数据快照；
- [ ] 记录计划动作、金额和理由；
- [ ] 在基金分析 Plus 和加密货币页面先行验证；
- [ ] 不接入交易账户、不执行交易、不保存第三方凭据。

### P1：根据观测结果推进

- [ ] 交易执行结果和交易后复盘；
- [ ] 基金与加密货币统一数据适配；
- [ ] 任务型导航；
- [ ] 最近使用和手动置顶；
- [ ] 高级搜索模板；
- [ ] 博客文章、项目和面试题关联。

### P2/P3：暂缓

- [ ] 账号体系和云端同步；
- [ ] 订阅和收费；
- [ ] 基金自动交易或加密货币自动跟单；
- [ ] 社区评论、私信和协作；
- [ ] 没有明确需求支撑的 `job`、`life` 业务扩展；
- [ ] 将基金登录入口作为正式认证基础设施。

## 9. 版本决策机制

每次迭代至少记录以下内容：

| 项目 | 说明 |
| --- | --- |
| 问题 | 当前要解决的具体问题 |
| 假设 | 为什么相信这个功能可能有效 |
| 最小实现 | 本轮只实现什么 |
| 观察指标 | 用什么判断是否有效 |
| 实际反馈 | 使用数据、主观感受和失败案例 |
| 决策 | 保留、优化、合并、降级或删除 |
| 下一假设 | 下一轮要验证什么 |

建议同步记录在 [`.claude/iteration-log.md`](../.claude/iteration-log.md) 中。

功能决策规则：

- 高频且能改善真实决策：优先投入；
- 高频但只是信息搬运：优先自动化或简化；
- 低频但能沉淀长期资产：小成本保留并观察；
- 低频、低价值且维护成本高：降级或淘汰；
- 只有猜想、没有使用证据：不得直接扩展成大模块。

## 10. 验收标准

### 阶段 0 验收

能够通过当前设备的本地记录回答：

- 每周真正使用哪些页面；
- 哪些页面只被打开，没有后续动作；
- 哪些外部跳转经常失败；
- 哪些数据页面最值得继续维护。

### 阶段 1 验收

能够回答：

- 我为什么做了这次操作；
- 当时看到的策略和数据是什么；
- 我是否按照计划执行；
- 结果与预期有什么差异；
- 这个策略是否值得继续参考。

### 阶段 2 验收

能够完成：

```text
进入网站
  → 选择任务
  → 进入常用工具
  → 使用搜索模板或站内能力
  → 减少重复查找和页面切换
```

### 阶段 3 验收

能够在限定时间内：

```text
按场景找到知识
  → 查看关联技术
  → 找到真实项目案例
  → 找到面试表达或练习题
  → 记录是否实际复用
```

## 11. 当前版本结论

当前项目已经形成若干可用闭环，但还没有形成统一的个人决策闭环。下一阶段的核心不是继续增加入口，而是验证：

1. 投资模块能否真正帮助完成交易前判断和交易后复盘；
2. 导航和聚合模块能否持续减少生活、工作和学习中的查找成本；
3. 博客、面试题和项目资料能否沉淀为可复用的个人知识资产。

产品演进主线为：

```text
现有信息门户
  → 个人高频工作台
  → 投资决策与复盘工具
  → 知识和工作流资产库
  → 基于真实使用结果的外部复用验证
```

本轮只落地规划文件，不修改业务代码、路由、数据源、依赖或认证边界。
