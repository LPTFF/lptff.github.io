# 业务任务分析执行规范

只在目标不清、方案有重大取舍、用户仍承担大量加工工作，或同类问题反复失败时展开分析。目标、范围和验收已明确的维护任务，直接修复并验证；不因涉及搜索、列表、筛选、报表或日志自动增加流程。

## 需要分析时

围绕当前缺口回答，已有信息直接复用，不要求逐项报告：

- 用户最终要完成什么任务、判断或体验，被请求的功能如何帮助它；
- 必要信息从哪里来、如何加工和呈现，缺失信息是否真的阻断当前任务；
- 方案减少哪些劳动，又增加哪些输入、等待、核查、维护和依赖成本；
- 交付后仍有哪些工作留给用户，是否有更简单且可恢复的办法；
- 哪个可观察结果能证明问题解决，哪些结论仍然未知。

取数更快、信息更多、文件可下载，不自动等于整个任务更容易。全量导出适合归档与交换；若目标是发现异常或作出判断，应验证比较、计算与判断是否得到支持。只比较影响本次取舍的成本，不要求等级、业务图或固定模板。

## 事实与取舍

- 目的不明时保留未知，不能把当前代码行为反向解释成正确需求。
- 只有缺口会改变范围、风险或方案时才询问用户；不重复询问已有授权与事实。
- 用户确认现有功能满足需要，可以支持维持现状；不要求先补收益量表或使用记录。
- 收益包括时间、信息价值与使用体验；成本包括人的阅读、核查、接管时间和运行费用。新增分析、文档或测试也需接受同样判断。

## 落到交付物

已确定的计算和检查放进程序；流程、边界与恢复落实到产品；有复发价值的失败转成最小回归案例。只将难以从交付物理解的原因、关键取舍和未实现边界留在现有资料，不建立第二份产品状态。

验证遵循[真实环境验收原则](trusted-verification.md)：预期来自用户任务、已确认规则或已核验结果，不能只复制当前实现作为答案。只报告证据覆盖的范围，区分规则正确、路径可用与长期收益。

[业务任务分析理论](../theories/agent-business-task-analysis.md)供遇到复杂错配时按需参考，不是普通维护的必读项，也不增加执行步骤。
